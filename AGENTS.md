# AGENTS.md

This file gives guidance to coding agents (Claude Code, Codex) working with code in this repository. `CLAUDE.md` imports it.

## Status

Phases 1 to 4 and the desk, integration and safety campaigns are built. [ROADMAP.md](ROADMAP.md) lists what shipped, what is still open and the parking lot. No CI or lint is configured yet.

- [docs/openag.md](docs/openag.md) — product notes (what OpenAg is, the locked feature set, the v1 ship bar)
- [ROADMAP.md](ROADMAP.md) — shipped and open work, parking lot

## Working rules

- Use ROADMAP.md for status. Keep changes within the scope of the request; record out-of-scope ideas under its Parking lot instead of building them.
- One focused commit per change, in Conventional Commits style (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`).
- Record what was verified in the PR description or in the relevant `docs/notes/` file. Do not claim checks that did not run.
- When a task says "verify", check the real npm package or docs (do not rely on memory) and record the findings in `docs/notes/` (e.g. `sqlite-vec.md`, `mastra.md`, `acp.md`).

## UI copy

- Keep routine controls and menus concise. Never add unsolicited disclaimer text about configuration scope, requested versus returned models, runtime confirmation or provider verification to normal UI, including tooltips and menu footers. Keep those explanations in help documentation. Show specific errors or actionable warnings only when the current state requires them; add explanatory UI copy only when the owner explicitly requests it.

## Native UI consistency

- Use the installed shadcn Base UI/base-nova components and official compositions throughout the desk. Shared tokens and explicit control-size variants own styling; feature classes own layout, not competing control skins or ancestor repairs. Before marking UI work complete, compare reachable rendered screens and states with those compositions and record coverage in the component audit. Component imports or a build alone do not establish visual consistency. Keep specialist graphics, remote-viewer geometry and semantic document content as explicit audited exceptions.

## UI status badges

- Use the shared `Badge` component and its semantic `variant` for status: `success` for affirmative states (Granted, Connected, Installed, Read verified), `attention` for unchecked, pending or needs-setup states, and `destructive` for denied, not-granted or failed states. Reserve `outline`/`secondary` for neutral metadata. Keep the label and variant consistent; use the variant rather than per-call colour overrides. Before completing a status UI change, check every reachable state against this mapping.

## Default bot knowledge maintenance

- For every feature, fix, removal or UI change, check what the default bot must explain differently. Update the affected product/help documentation and bot-facing guide or tool descriptions in the same change, before the change is merged.
- Maintain the release handbook in `docs/help/` (manifest plus topic Markdown); `pnpm -r build` packages it and `node scripts/verify-bot-knowledge.mjs` checks delivery and policy. Use `docs/openag.md` for product concepts and the relevant `docs/notes/` document for feature behavior, setup, UI locations, permission requirements and known limits. Keep one authoritative explanation per topic; link to it from the bot-facing knowledge rather than maintaining separate copies.
- Keep any runtime knowledge loader/index in sync with those sources. Verify the changed content reaches whichever bot is configured as default, including existing installs; a documentation edit alone is not proof the bot can read it. Until that delivery path exists, record the gap explicitly in the PR description and handoff.
- Describe implemented behavior from code and verification evidence. Label planned, unavailable and unverified capabilities explicitly; keep source changes, deployment and live acceptance distinct. Obtain changing installation state through scoped read-only tools, not static prose.
- Keep credentials, tokens and private user data out of shared product knowledge. Knowledge access grants no new action permissions; existing policy and approval gates still apply.
- In the PR description or handoff, list the knowledge sources updated and how delivery was checked, or state why the change needs no knowledge update.

- For search, computer or notification capability changes, read `docs/notes/capabilities.md` and run `node scripts/verify-capabilities.mjs`. Keep tool offering and diagnostic reasons derived from the same definition; catalogue reads use passive state.

## Hard safety invariants

- Permission sessions (`permissions.ts`) are the action authority: Read Only/Ask, Workspace Write/Ask and Full access/Never. Explicit review under Never is refused. The daemon enforces filesystem writes where supported; opaque worlds are unavailable in confined modes. Native ACP execution is disabled. Category settings are an immutable migration archive and their API returns 410. Upgrades require owner adoption before tools; fresh installs use Workspace Write. See `docs/notes/permission-sessions.md` and `docs/notes/permission-worlds.md`. Mode changes expire pending reviews, cancel supported active execution and replace cached adapter context; they never undo effects or clear Unknown.
- Unknown tools classify as `act-external`; absent a daemon-owned requirement they require explicit review, which Never refuses. Classes remain effect metadata for independent ceilings and receipts, not category permission authority.
- MCP completion follows protocol results independently of permission classification; `effectVerification: not-checked` records downstream verification separately. Lost/interrupted invocations can still be Unknown. Never replay historical actions automatically.
- Secrets never reach the DB, ledger, turn state or logs unredacted: `redact.ts` (`getDefaultRedactor()`) is applied inside `ledger.append`, `approvals.request/resolve`, turn `state_json` and adapter stderr. Any new write path (memory, vectors, settings, device tokens via `addSecret`) must go through it. User messages are redacted before bots see them.
- Clients never hold their own DB copy; the daemon owns the only one.
- Auth (`auth.ts`): `owner-credential.ts` resolves a private persistent OWNER secret (`.owner/credential.json`, mode 600 in a mode-700 directory), importing an existing `OPENAG_TOKEN` without rotation; `owner-access.ts` grants single-use Full pairing links only over the protected host Unix socket, and `pnpm desk:open` opens the local browser without reading the secret. No loopback HTTP ownership bypass or bot recovery tool. See `docs/notes/owner-access.md`. Browsers/phones hold per-device `oag_` tokens (stored only as SHA-256, shown once; `redact.ts` matches the `oag_` pattern). Devices are added by single-use 8-char pairing codes (5 min, max 5 active) redeemed on the unauthenticated `POST /pair` (4 KB body cap, failures-only rate limits per client + global, only the LAST `X-Forwarded-For` entry from a loopback peer is trusted). Each device records `created_by`; `DELETE /devices/:id?cascade=1` revokes the whole chain and closes open sockets (WS code 4001). All routes have a 1 MB body cap. ACP adapter processes never inherit `OPENAG_TOKEN` (`withoutOwnerSecrets`). Add new top-level API routes to `API_SEGMENTS` in `static.ts`.
- openagd as MCP server (`mcpserver.ts`, `POST /mcp`): ACP bots get it in `session/new` under a per-connection name `openag-<hex>` with a scoped `oagt_` token (per bot+room, hash-only, valid only while that pair has an active turn). Every call goes through `ctx.callTool` (the server is the authoritative gate; the ACP permission handler auto-allows only the exact own-server tools in the allow-list, so there is one approval per action). First-party tools are wired once in `tools/firstparty.ts` so the MCP list, API runtime and runner executors cannot drift. Approval waits are bounded and expired on timeout, disconnect or turn end (not on shutdown). Details: `docs/notes/mcp-server.md`.
- MCP client (`mcp.ts`, config ONLY in `$OPENAG_DATA/mcp.json`, refused if group/world-writable or not owned by the daemon user; the only HTTP writes are the OWNER/Full-only desk routes for CUSTOM REMOTE (http) servers, `POST/PATCH/DELETE /mcp/servers[/:id]`, through the shared writer `mcp-config-write.ts` (`.integration-setup.lock`, digest compare-and-swap, raw-item edits, backup, audit); a local command (stdio) is written only through the owner's command review below, hand-written commands and built-in/connection entries are read-only there): tools become `mcp.<server>.<tool>`, class `act-external` unless an owner-file `toolClasses` declaration or reviewed daemon-managed declaration says otherwise (exact server + original tool name; server hints/annotations are ignored; `policy.setAdminToolClasses`). See `docs/notes/mcp.md` for classification precedence and returned evidence versus effect confirmation, results are wrapped `{untrusted:true,...}` and capped, stdio children get ONLY PATH/HOME/LANG/TMPDIR + declared env (`${NAME}` refs; a missing var skips the server, which keeps Brave inert without a key), crashes/hangs are isolated. `classify()` and tool lookup use own-property checks (names like `constructor` must never resolve through the prototype chain). Custom remote servers (OA-454, `mcp-servers.ts`, `mcp-check.ts`, `mcp-forwarding.ts`, `mcp/ssrf-fetch.ts`, ADR 0003): https only, `allowPrivateNetwork` is a per-entry opt-in, link-local/metadata/reserved addresses are always blocked, the guard pins the connect-time lookup and never follows redirects; a header may reference only `OPENAG_MCP_<NAME>` variables when newly added (existing references stay unless the URL origin changes) and any other daemon secret is refused at load (`isDaemonSecretEnvName`, shared with the bot env stripper); `offerToAgents` (default true) forwards a ready server's tools to every ACP bot over `/mcp`, each call still goes through the gate (MCP operations are refused in confined permission modes and run without a fabricated approval in Full access); a server check is an `act-external` approval (`mcp_server_check`, source `mcp-server-check`, stored payload runs, no receipt start, 5 min expiry, max 5 pending) and registers nothing; edit/remove/disable expires that server's pending approvals. OAuth for custom remote servers (OA-457, `mcp-oauth.ts`, `docs/notes/mcp.md`): an http entry may carry `oauth: {scope?, clientMetadataUrl?}` (no secret in the file); the owner/Full-only routes under `/mcp/servers/:id/oauth` start, poll, cancel and disconnect a sign-in and store an owner-entered client (write-only). Tokens, client info and the registered client live only in `connector-mcp-oauth.enc` (connector key, no second key), per server id, issuer and ORIGIN (a changed origin, removal or turning OAuth off deletes them; an id reused later inherits nothing). Every OAuth request uses the guarded fetch with the entry's `allowPrivateNetwork`; discovery is refused unless the issuer equals where it was discovered, PKCE S256 is advertised, the authorization-code flow is supported, the resource is on the server's origin and every endpoint is acceptable. Registration order: owner-entered client, client metadata document (only when the owner set an https URL and the server advertises support), dynamic registration. The callback comes only through the managed route (hosted mailbox, Tailscale or operator-configured, the shared `/composio-connect` path dispatched by exact single-use state), never from Host or forwarded headers; state is 5 minutes, single use and device-bound, and `state` and RFC 9207 `iss` (required when the server advertises it) are checked BEFORE the code is exchanged. MCP requests carry a bearer from ONE single-flight token manager (no SDK `authProvider`, fresh clients per call); a 401, a 403 insufficient_scope or a rejected refresh makes the server `needs sign-in` (a network failure or 5xx keeps the grant) and the request that found out is never retried or replayed. Disconnect clears local state only; provider revocation is unconfirmed. Desk local commands (OA-456, `mcp-command-review*.ts`): `POST /mcp/servers/command-review` is owner/Full-only and only PROPOSES an `act-external` approval (`mcp_command_review`, source `mcp-command-review`, no turn, 5 min, max 5 pending) that carries the resolved program (realpath), arguments, env NAMES with their `${OPENAG_MCP_*}`/`${secret:NAME}` templates, the working directory `$OPENAG_DATA/mcp-work/<id>` and a sha256 of that spec plus the content of up to three existing absolute-path script arguments; shells, wrappers, bare interpreters and inline code are refused, an interpreter's script must exist (absolute path), a `#!` program is hashed too, loader env names (PATH, NODE_*, LD_*...) are refused and no reference is allowed in the program or arguments; only the owner may decide the approval. Only an accepted approval writes the stored payload (rebuilt and re-hashed at write; a stale or changed review is refused) as an entry marked `managedBy: "desk"` with its `review`; the loader recomputes the hash, the program realpath and every reviewed file's content at load AND before each spawn, so an unreviewed, edited or tampered desk command is `invalid` and never starts. Spawn is the resolved executable through `ExactEnvStdioTransport` (PATH/HOME/LANG/TMPDIR plus declared env, no shell). A command change is a new review (PATCH cannot change it; switches, timeout and removal need none); operator-written commands carry no marker, cannot be edited, replaced or removed from the desk, and run as before. Direct secrets (OA-455, `mcp-secrets.ts`): `${secret:NAME}` in an http header resolves from `connector-mcp.enc` (connector key, no second key), per server id AND origin, in one pass with env references; write-only owner/Full routes under `/mcp/secrets` (names and last four only); an origin change or removal deletes the server's secrets; unset, unbound or unreadable fails closed (`missing secret NAME`); values are registered with the redactor and never reach `mcp.json`, the DB, ledger, approvals or any process env; a desk command's env may name them too (bound to its reviewed program and arguments). `GET /mcp/servers`, `POST /mcp/reload`. Shared client callbacks, input contracts, catalogue refresh, task-only diagnostics and bounded result evidence follow `docs/notes/mcp-lifecycle.md`; server interactions are owner/Full-only invocation input, never Work pauses or action grants.
- Computer (`computer.ts`, `docs/notes/cua.md`): ONE Cua Linux sandbox (`openag-main`, `cua sandbox create linux --tier slim --browser`, no Docker) driven through the `cua` CLI via `execFile` with only PATH/HOME/LANG/TMPDIR in the child env. EVERY computer call goes through one mutex (`computer.withLock`; `cua do` has a GLOBAL target). `cua do` output is text (use exit codes: 0 ok, 1 failed, 2 bad args, 3 not found); lifecycle/screenshot/exec are name-addressed with JSON. `destroy` retries `rm -f` (real cua is flaky after suspend/resume) and verifies with `info`. `GET /computer`, `POST /computer/start|stop` (202, 409 when busy), `DELETE /computer` (owner only), `GET /computer/screenshot` (PNG, no-store). Screenshots live under `$OPENAG_DATA/computer/screens/` (newest 50). Computer tools (`tools/computer.ts`, registry `ToolDef`s): `computer_screenshot` (browse, returns a RELATIVE path, never bytes; `GET /computer/screens/:name`), `computer_click|type|key|scroll|open` (act-local; free text always after `--`; `open` is http(s) only), `computer_shell` (act-external, output wrapped untrusted, capped, `timedOut` flag). Every action runs `cua do switch <name>` first, inside the mutex. `computer.setInputGuard(fn)` makes actions/shell fail with `paused` (the takeover lock plugs in there); screenshots/status are never guarded. Remote input cannot enforce the host filesystem boundary and is unavailable in confined modes. Interactive Full access permits input without per-action prompts; takeover still blocks it. A form submission cannot be classified reliably from pixels.
- Computer backends (`computer/{driver,router,backends,browserbase,cdp}.ts`, `docs/notes/browserbase.md`): the daemon's `Computer` is a ROUTER over backends chosen by the OWNER-only `computer.backend` setting (`cua` default; `browserbase`, `docker` and `ssh` optional). Cua keeps its own implementation; the Docker backend is `computer/x11.ts` (xdotool/ImageMagick over an injected `exec`, argv only, never a shell string; reusable by the SSH backend) plus `computer/docker.ts` (docker CLI argv, child env limited to PATH/HOME/LANG/TMPDIR/DOCKER_*, no --privileged, no host mounts, no published ports; image `docker/computer/Dockerfile` is UNTESTED); the SSH backend is `computer/ssh.ts` (same X11 layer; env-only config `OPENAG_SSH_*`, key file mode 600, strict known_hosts, `-F /dev/null`; the remote command line is fixed words + base64 decoded by POSIX sh so typed text is inert in any login shell; stop/destroy only detach); every other backend is a small `ComputerDriver` wrapped by `createDriverComputer` (same mutex, input guard, screenshot validation, redaction, audit). Credentials come ONLY from env (`BROWSERBASE_API_KEY`...), never the DB/API, and are stripped from bot processes; an unconfigured backend is inert (never created, never contacts anything). The router never switches while busy, while a human holds control, or while a `computer_*` approval is pending, and releases a HOSTED (billed) session when switching away and at shutdown. Capabilities (`shell`, `view: proxy|external|none`, `hosted`) drive the tools (`computer_shell` is not offered without a shell) and the desk. An EXTERNAL takeover returns the backend's live-view https URL (checked by `isSafeExternalUrl`, never logged/stored, no cookie, no proxy); revoking its holder releases the hosted session because that link cannot be revoked.
- Human takeover (`takeover.ts`, `computerview.ts`, `docs/notes/cua.md`): `POST /computer/takeover|handback`, `GET /computer/takeover` (Bearer). While a human holds the lock the input guard returns `human has control` (screenshots still work); in-memory state, `takeover` events in `_system`, 30 min idle release, released when the holder's device is revoked. `/computer/view/*` (HTTP + WS reverse proxy to the sandbox viewer, loopback-pinned) is authenticated ONLY by the HttpOnly `oag_view` cookie from takeover, never by Bearer; the viewer ticket is a credential that appears only in the takeover response.
- Nightly reflection (`reflection.ts`, `reflection-apply.ts`, `reflection-schema.ts`, setting `reflection`, OFF by default, `docs/notes/reflection.md`): the isolated UNATTENDED turn returns validated proposals with no tools. The daemon saves memory notes automatically through redaction + `commitMemory`, without an approval; owner/Full users can remove notes in Saved memory. Skill drafts still require accepted/edited approval in the originating conversation. The `approval_decided` subscriber also handles legacy pending memory approvals; these are never auto-accepted. Ignore/respond/expiry never apply proposals. Removal does not erase conversation or prevent relearning. `memory_append` is the interactive managed writer, available only in interactive Full access until its world supports confinement, and is exposed to ACP bots over MCP. Claude's own auto-memory is disabled for bot processes (`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`): it wrote under `~/.claude` with no permission request.
- Skills (`skills.ts`, `tools/skills.ts`, `docs/notes/skills.md`): agent-owned SKILL.md files retain approved versioned writes and managed no-symlink paths. The optional owner-enabled `~/.agents/skills` library is read-only through skill tools, with explicit per-agent assignments and source-qualified identities. `skill_list` finds assigned entries beyond the bounded index; `skill_load` reads instructions or bounded in-package UTF-8 references, always untrusted/redacted and gated. All package paths stay in `skills.ts`. Source/assignment changes invalidate cached ACP sessions; resumed configuration changes discard old session ids. Native Claude skills are filtered with an empty allowlist; Codex native instructions/bundled skills/search are disabled in child configuration. Verify installed adapter behavior on upgrades. Assignments are not a filesystem sandbox, and external edits are not revision-pinned. Reflection stays isolated and proposes only agent-owned skills; it never writes the shared library.
- Public ingress (`hooks.ts`, `automations.ts`, `docs/notes/hooks.md`, `docs/cloudflare-tunnel.md`): `POST /hooks/:slug` is the unauthenticated automation ingress. Besides `/pair` and `/health`, `GET /composio-connect` is the narrow OAuth exception described below; it can only finish an already authorized pending attempt. Automations have a `trigger_kind` (cron|webhook|github|slack). Verification is over the RAW body before parsing (webhook: `X-OpenAg-Secret` stored as a SHA-256 hash; GitHub `X-Hub-Signature-256`; Slack v0 signature + 5 min skew; github/slack raw secrets are stored because HMAC needs them and are registered with the redactor, 12+ chars), unknown/disabled/bad look identical (401), failures are rate limited per client, unknown-slug probes have their own small budget, bodies are capped (256 KB), only accepted deliveries are de-duplicated. A hook (or `output_mode=wake` watcher) run is UNATTENDED and ISOLATED by default (no tools; for Claude also the built-in tools are disallowed in `_iso-<id>` rooms), has its own hidden room, is never vector-indexed, cannot allowApprovals, and its output goes ONLY through the wake filter (dedupe per source, pings labelled "(via name)"). The event payload is embedded redacted and clipped as untrusted data. Cron + `room` automations are unchanged.
- GitHub polling (`githubpoll.ts`, automations `trigger_kind = 'github_poll'`, `docs/notes/github-poll.md`): OUTBOUND ONLY, no tunnel. ALL requests are built in `githubpoll.ts`: fixed host `api.github.com`, strict repo regex, `redirect: "error"`, token only in the Authorization header (token alphabet `[A-Za-z0-9_-]`), fixed short error strings (never the body), first poll only records the cursor, ETag + `X-Poll-Interval`, back-off bounds. The raw token is stored in the DB (registered with the redactor, never returned by any API). A poll that finds new allowed events starts ONE unattended, isolated run (no tools, ever: `allowTools` is refused for polls), offline, never indexed, output only through the wake filter. Hook runs with `allowTools` are read-only AND offline (`noNetwork`; Claude built-ins disallowed in `_hook-` rooms). Notifications mode is NOT implemented (it needs a classic token).
- Apps (`apps.ts`, `docs/apps.md`): owner-installed folders `$OPENAG_DATA/apps/<id>/` (copy only; no HTTP install). Enabling is OWNER-only and bound to a sha256 of the WHOLE folder (manifest + code, `data/` excluded, symlinks refused, caps 200 files/5 MB), re-checked on every call and read fresh at enable. Tools run out of process (`app_<id>_<tool>`, declared class, never `secrets`; argv fixed by the manifest, bare interpreters rejected, model args only on stdin validated by a strict schema, minimal env + declared names, never `OPENAG_*`, process-group kill, capped output, stderr discarded, results wrapped untrusted). `policy.setAppToolClasses`; `requires: [ENV]` keeps an app inert. ACP sessions are invalidated only when the enabled set changes. The Composio bridge is just an example App (`examples/apps/composio`, `docs/composio.md`), optional.
- Composio OAuth (`composio-connect.ts`, `signin-routes.ts`, `docs/composio.md`): optional fixed hosted MCP connection `composio-connect`; SDK public-client OAuth/PKCE, device-bound single-use state, encrypted `connector-composio.enc` using the stable private `.connectors/key`. Normal Connect has no address form. The daemon uses an automatically discovered private Tailscale Serve callback, or a hosted callback mailbox only when the operator sets `OPENAG_SIGNIN_RELAY_URL` (no built-in relay); operator mode/legacy environment overrides remain available. A started attempt pins its route. The original Full device polls its own attempt; hosted retrieval uses a separate daemon-only random credential. The hosted relay seals callback codes to a per-attempt daemon public key before database storage, retains only short-lived ciphertext/public material, never PKCE verifiers, provider tokens or owner/device credentials; no arbitrary return redirects. The callback tab has no device login. Both routes recheck current initiating Full authority before exchange and saving. Tailscale adds/reuses only the callback path, preserves unrelated Serve routes, refuses conflicts/Funnel, and never enables public ingress. No passive status/catalogue read prepares routes or contacts the relay. Legacy configured callback/desk settings and authenticated completion remain compatible; registrations and working credentials survive failed reconnect/migration. Owner/Full-only POST start/status/cancel/complete/disconnect under `/connectors/composio`; direct `GET /composio-connect` remains registered before Bearer/static with bounded single-use state, no-store/no-referrer. The reserved MCP id, act-external gate and no-replay behavior remain. Disconnect clears local access; provider grant revocation is unconfirmed. Preserve legacy API-key Apps. Source/controlled acceptance does not establish hosted deployment or real consent.
- Room router (`router.ts`, `docs/notes/router.md`): per-room `router` strategy, owner-only, only for messages with no @mention, answer must be a room member, any failure -> lead, message redacted + clipped, fixed hosts, keys from env only.
- Ollama chat bots (`runtimes/ollama.ts`, `docs/notes/ollama-chat.md`): `model: "ollama/<name>"` on an api bot; every tool call through `ctx.callTool`; `OPENAG_OLLAMA_URL` is separate from embeddings.
- Slack channel (`slack.ts`, `ingress.ts`, setting `slack`, OFF by default, `docs/notes/slack.md`): Socket Mode, outbound only. Tokens ONLY in env (`SLACK_APP_TOKEN`, `SLACK_BOT_TOKEN`, registered with the redactor). Only the ONE configured channel and an explicit allow-list of Slack user ids (empty = nobody; setting is OWNER-only) reach a room, as ordinary user messages (actor `slack`, `[Slack]` prefix, rate limited, de-duplicated) through the same `ingress.post` as the desk, so the policy gate and approvals are unchanged. Approvals are never decided from Slack (it only gets "waiting in the desk"). Only replies to Slack-originated turns go back, into that message's thread, escaped (`& < >`) with parse/unfurl off; fixed hosts, `redirect: "error"`, the socket URL must be wss on a Slack host. WebRTC (OA-214) is design + spike only (`docs/notes/webrtc.md`).
- WebRTC (`rtc.ts`, setting `rtc`, OFF by default, owner-only, `docs/notes/webrtc.md`): a phone reaches the SAME gateway over a data channel with no VPN. Signaling is a secret ntfy topic (never listed, rotated on device revoke); offers AND answers carry an HMAC over the DTLS fingerprint (exactly one sha-256 fingerprint line allowed); the pair key is a random per-invite secret, never the 8-char code. A `pair` peer can only `POST /pair` / `GET /health`; a `device` peer is bound to one device token (the owner token is refused), limited to an allow-list of paths checked on the PARSED path (no `%`, `//`, `\\`), never `/settings`; frames, responses, peers, rates and lifetimes are capped; no frame handler may throw into the process.
- Always-on operations (`backup.ts`, `ops.ts`, `runtimes/runner.ts` watchdog + budget, `docs/ops.md`, `docs/backup.md`): daily verified online SQLite backups (one self-contained mode-600 file, partial files never carry a final name, optional mirror only into an existing absolute `OPENAG_BACKUP_DIR`, `POST /backups/run` owner-only); the turn watchdog fails silent turns (never one waiting on a pending approval); the optional turn budget (`limits` setting, OFF) counts turns not dollars and never blocks a resumed turn; `OPENAG_HEALTHCHECK_URL` is an https secret whose PATH is registered with the redactor (the redactor ignores values that look like URLs, so never `addSecret` a URL); service logs rotate in place; `OPENAG_RTC_*`, `OPENAG_HEALTHCHECK_URL`, `OPENAG_BACKUP_DIR`, `SLACK_*` and every `*_API_KEY` are stripped from bot processes.
- Desk owner actions: a LIMITED device cannot use OWNER-only routes (403). Normal first sign-in/recovery uses `pnpm desk:open` on the daemon host or approval from a trusted Full device; no remembered owner token is required. Settings, Devices, "Access & recovery" explains this and nests the old token-paste route under "Legacy owner token". That compatibility token stays in MEMORY ONLY (`ownerSession.ts`, never storage/cookies/URL), retries only the request refused with "owner token required", clears on a 401, and is never used over WebRTC. Auth failures from an old browser session must not clear a replacement session. See `docs/notes/owner-access.md`.
- Device access (`auth.ts`, `devices.access`, `pairing_codes.access`): every device is `limited` (default) or `full`. A `full` device is treated as the owner by the gateway (the owner TOKEN is never copied; the flag lives in the DB and goes with the device, so revoking the device ends it). The desk's owner-token login mints its device as `full` (`POST /devices {access:"full"}`, owner only); pairing codes are `limited` unless the owner (or a full device) creates them with `access:"full"`; `PATCH /devices/:id {access}` changes a live device (owner only). `/whoami` still reports `kind: "device"` with its `access` (the desk must not re-mint on reload). WebRTC peers stay limited to their path allow-list whatever their access. Never treat "loopback" alone as owner.
- Questions and explicit approvals/provider prompts belong to their originating conversation; Needs you and recovery acknowledgements are removed. Answers grant no action permission. See `docs/notes/chat-interactions.md`.
- Settings pages (desk `SettingsLayout`, `#/settings[/models|proactive|devices|memory]`, `#/bots`, `#/connectors`, `#/automations`): Devices owns pairing, access, session and recovery; Server remains the default Settings page. For device UI behavior, read `docs/notes/devices.md`. extra daemon routes are read-mostly. `GET /models/status` (`models.ts`) reports CLI adapters, which provider env keys are SET with the LAST FOUR characters only (never a value; keys stay env-only and are never accepted over HTTP) and Ollama reachability; nothing there runs a command. `GET/PUT /bots/:id/memory` (PUT owner-only, redacted, 16 KB cap, committed via `commitMemory`, audited by length only), `GET /memory/search` (503 without embeddings), `POST /wake/decisions/:id/feedback` (review flag only, column `wake_decisions.feedback`). Segments `models` and `memory` are in `API_SEGMENTS`.
- Default bot (`defaultbot.ts`, setting `defaultBot`, `docs/notes/default-bot.md`): created ONCE at first start (handle `bot`, name "Bot", no room, no turn, adapter by module resolution only) and used by heartbeat and reflection when their Bot setting is empty; they never read room `main`. A missing default skips the run (no fallback). `PUT /settings/defaultBot` is owner/full-device only and the bot must exist.
- Conversation model (`rooms.kind` `room`|`direct`, migration 021, `delivery.ts`, setting `deliveryRoom`, `docs/notes/conversation-model.md`): rooms are optional and `kind` is never inferred from the member count (`POST /rooms` without `kind` makes a `room`; `kind:"direct"` needs exactly one bot and reuses that bot's direct chat). Pings, the brief and reflection proposals go to `resolveDeliveryRoom` (the owner's `deliveryRoom`, else the default bot's direct chat, created on demand); a destination that is set but gone resolves to nothing: pings become digest items (`no_destination`), the brief is not sent or consumed, reflection proposals stay in `_reflection`. Nothing names room `main` except the explicit dev seed; `install-service.sh` seeds only with `OPENAG_SEED_SAMPLE=1`. The desk's address-less route is `home` (opens the default bot's chat).
- Readiness (`readiness.ts`, `GET /readiness`, owner-only `POST /readiness/apply`): a live checklist of what makes the agent always-on; apply flips ONLY heartbeat, reflection and the brief (reflection automatically saves validated memory; skills need approval), never push, Slack, WebRTC or anything needing a secret.
- Push (`push.ts`, setting `push`, OFF by default): ntfy JSON publish to the server ROOT with the topic in the body; automatic triggers are new approvals, open provider-response requests and wake pings; text is minimal (bot + tool name for approvals, bot + generic response-needed text for provider input; ping reason only with `includeDetail`); the topic is a secret (random 128-bit, registered with the redactor, masked in audit events); rate-capped; failures never affect turns. `POST /push/topic|test`, `GET /push/status`.
- Unattended (scheduled) turns — `runner.run(..., { unattended: true })`, e.g. the heartbeat — can only use read/search/browse tools that are already `auto`; everything else (act-*, secrets, unknown) is denied WITHOUT creating an approval, independently of interactive presets, unless the turn also has `allowApprovals`. Delegated/result turns inherit the flag. Scheduler (`scheduler.ts`: no catch-up, overlap guard, 5-field cron only) and settings (`settings.ts`, table `settings`, `GET/PUT /settings/:key`, `OPENAG_TZ`) drive the heartbeat (`heartbeat.ts`, OFF by default, hidden room `_heartbeat`). Rooms whose id starts with `_` are hidden from `GET /rooms`. Heartbeat output goes through the wake filter (`wake.ts`): a validated JSON verdict (`silent|digest|ping`, urgency, dedupe_key) is run through, in order, dedupe -> (for pings) active hours -> urgency threshold -> daily budget; each rule downgrades a ping to a digest item (`digest_items`, consumed by the morning brief), every decision is one `wake_decisions` row + one `wake` event in `_system` (`GET /wake/decisions`), a delivered ping is a Primary `message` in room `main` and calls the optional `onPing` hook (push, OA-118). Unparseable output is `silent`/`invalid`. The morning brief (`brief.ts`, setting `brief`, default 07:30 local, window of 3 h, once per local day) is built deterministically in code (no model turn) from undelivered `digest_items` + pending approvals and posted as a Primary message in `main`; empty -> nothing sent; `GET /digest`, `POST /brief` (force). Automations (`automations.ts`, table `automations`, `/automations` CRUD + `POST /automations/:id/run`) are cron + bot + room + prompt objects run as UNATTENDED turns (`allowApprovals` opt-in per automation); 5-field cron only, minimum interval 5 minutes, max 50, bot must be a member of a non-`_` room; the manager keeps one scheduler job per enabled automation (`scheduler.unregister`).
- Receipt conflicts: daemon-owned path scopes protect overlapping writes across chats/bots; bounded reads remain available. Opaque and historical unscoped writes remain conservative. Owner inspection invalidates conflicting proposals only and preserves Unknown. See `docs/notes/daemon-execution.md`.
- ACP native effects and inherited integrations are disabled or refused. Sessions use `settingSources: []` with Claude `default` / Codex `read-only` as defensive adapter settings, failing closed on unsupported setup. Only exact offered own-server tools can forward with `allow_once`; the daemon permission session decides execution. Never select `allow_always`. See `docs/notes/acp.md`.

## Integration onboarding convention

- Use GLOSSARY.md terms: owner/device access, integration connection, provider account, connected service account, trusted app address. Provider consent never establishes OpenAg ownership or tool approval.
- The daemon manages internal keys and token lifecycle. Reuse the existing private connector key and encrypted stores; preserve legacy key material, ciphertext and registration callbacks. Missing original state requires explicit recovery, never silent rotation.
- Select callbacks through the daemon-managed hosted/private routes or explicit operator configuration; browser/Host/forwarded input must never select the callback origin. Normal users enter no callback/desk addresses. Plain phone browsers cannot use the daemon's loopback address. Keep unavoidable provider client-registration prerequisites in operator setup, separate from ordinary Connect/consent.
- Add only the integration being requested. Preserve the central policy gate and do not introduce a generic connector framework without a concrete need. Update delivered help and verify the actual flow through controlled integration checks.

## Integration evidence and claims

- **Scope every claim.** Say what each check covers. Report these separately and never merge them into "tested and working": controlled/automated checks, live provider acceptance, deployment, and user-confirmed use. A passing read says nothing about writes, other tools, or other connectors.
- **Trace the path before changing it.** For runtime, MCP, adapter or connector bugs, first list the layers the action crosses (adapter, OpenAg policy gate, MCP transport/session, provider consent, result reporting) and state which layer each check exercises. Do not assume fresh-session behavior holds for reused sessions.
- **Fix the class, not the instance.** After a bug, name the shared contract it belongs to (tool names, schemas, classification, session reuse, completion reporting) and check the other adapters, tools and cases that share it, in the same change.
- **One real journey first.** For an integration change, run one bounded end-to-end journey through both real adapters, including a second call in the same session, before widening coverage or writing broader tests. Fixtures and OSS research are not acceptance evidence.
- **Don't let the harness lie.** A test must fail when the nested or provider result fails, and must not be bypassable by native tools. Watch the event that actually proves the outcome. Don't run tests concurrently when an uncertain receipt can block another.
- **Stop on uncertainty.** On an unknown outcome, do not retry, auto-recover, or start a fresh investigation. Report the failed stage, invocation IDs, approval state and sanitized provider response, then wait.
- **Report coverage.** For connector work, state whether discovery / authenticated read / provider prompt / write were verified, unverified or not applicable. Writes need an approved disposable target.

## Architecture (big picture)

- **openagd** is a single Node/TS daemon on the host machine and *is* the product. Web desk, phones and webhooks are thin clients; there is one brain and one DB.
- **Two bot runtimes** behind one `BotRuntime { runTurn(ctx) }` interface (`runtimes/types.ts`):
  - `ApiRuntime` — API models via Mastra.
  - `AcpRuntime` — subscription CLIs (Claude Code, later Codex) over ACP; they run their own agent loop. One ACP session per (bot, room); adapter child process is spawned with cwd `$OPENAG_DATA/bots/<id>/work/`.
- **Every tool call goes through one policy gate**: `ctx.callTool` → daemon-owned operation requirement + effective permission session → execute | review | refuse. `ask` creates a row in `approvals` and pauses the turn until an explicit decision in its conversation resolves it (accept / edit / respond / ignore). Runtimes must never invoke tools directly. ACP exposes the scoped own-server tools and refuses native effects; the daemon gate is authoritative for their execution. `runtimes/runner.ts` owns turn lifecycle (`turns` rows, `turn_started/finished`) and gate wiring.
- **Ledger**: append-only `events` table per room (`ledger.ts`: `append`, `list`, `subscribe`). It is the record of everything and the visible Primary ledger; the gateway's `/stream` WebSocket pushes it.
- **Storage**: one SQLite file (WAL, foreign keys, sqlite-vec) at `$OPENAG_DATA/openag.db`, numbered migrations in `apps/daemon/src/db/migrations/NNN_name.sql` tracked by `schema_version`. Tables: `bots, rooms, room_members, events, approvals, turns, tool_modes`. Pending approvals live in the DB so they survive restarts. Restart survival: `runner.recover()` (startup) and `runner.shutdown()` (SIGTERM, called *before* runtime teardown) mark in-flight turns `interrupted`; accepting an approval for an interrupted turn resumes it (ACP: `session/resume` with the saved `acpSessionId`, falling back to a fresh session) with a one-time `pregrant` (same tool + same file_path/command) so the re-issued call doesn't ask twice. A pregrant replaces only an `ask`, never a `deny`. Only turns waiting on a pending approval resume.
- **Memory** (Phase 2): per-bot `MEMORY.md` (capped head in prompt, hand-editable) + sqlite-vec index; facts → MEMORY, repeatable workflows → versioned Skills.
- **Gateway** (`gateway.ts`, Hono): Bearer-token REST (`/rooms`, `/rooms/:id`, `/rooms/:id/messages`, `/rooms/:id/events`, `/bots`, `/approvals`) + `/stream` WS (token in query). Unauthenticated: `GET /health` (vec_version) and the static desk (`static.ts` serves `apps/desk/dist`: `/assets/*` immutable, everything else `no-store`, no dotfiles, no traversal, 503 if not built). **When adding a new top-level API route, add its first path segment to `API_SEGMENTS` in `static.ts`** so a desk file can never shadow it. `/bots` never exposes `config` or `instructions`. Room addressing: `@name` → those bots, `@everyone` → all members, none → room lead; `@` inside an email address must not match.

Layout: `apps/daemon/src/{db,ledger,rooms,addressing,policy,approvals,gateway,main,seed}.ts`, `src/runtimes/{types,gate,tools,pregrant,runner,api,acp}.ts`, `src/tools/{registry,files,brave,index}.ts` (first-party tool registry: `ToolDef` with class + zod schema; `runtimes/tools.ts` is a re-export shim), `src/{prompt,delegation,redact}.ts`, `apps/desk/` (React 19 + Vite 8 SPA: hash routes, one shared WebSocket via `StreamProvider`, all ledger content rendered as React text, hand-written manifest + shell-only `public/sw.js` that never touches API calls), `scripts/` (e2e, launchd), `docs/notes/` (verified findings: sqlite-vec, mastra, acp).

## Product constraints worth remembering

- Don't invent a new agent loop; Composio is an optional bridge, never the only path; proactive pings need a "worth waking" filter.
- v1 ship bar (Phase 3 target): 1 Primary + ≥2 specialists + 1 computer (Cua managed default; Browserbase/Docker/VPS optional) + SQLite/MEMORY/vectors + nightly reflection + Skills + in-chat approvals + morning Heartbeat + cron + ≥1 external automation trigger + LAN + Tailscale + CF Tunnel for `/hooks/*`.
