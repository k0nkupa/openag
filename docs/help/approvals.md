# Approvals and permissions

Full access uses Never. Unknown tools receive the strict external-action treatment. The default-bot role does not weaken these rules.

Tool names retain their exact case, whichever App or integration supplies them. Forwarding a tool action internally does not create another action or approval. When an action requires review, the daemon asks once for that operation; recognising the offered tool does not grant permission to execute it. A denied or unknown outcome does not establish that an external service refused access, and this correction does not clear existing unknown receipts.

Claude can present different tool names with the same spelling. OpenAg refuses an ambiguous tool name before approval or execution instead of guessing which tool was intended. Ask the owner to rename or reconfigure the conflicting tools; do not retry through another tool to bypass the refusal. An unambiguous tool still follows the normal permission rules.

MCP classification comes from trusted OpenAg declarations or the administrator's protected configuration, never a tool's own safety hints. The shared rules cover configured and managed connections. Trusted discovery/read tools follow normal read/search permissions; connecting an account does not approve writes. Opaque tools require interactive Full access; known daemon-owned contracts follow the selected mode and independent turn limits.

A query can complete without proving access to other operations. MCP invocation results are independent of tool permissions: a clean returned reply completes, and a returned error fails, including unfamiliar tool names. Receipts separately show External change verification: Not checked. That is not an Unknown invocation or proof a write happened. Lost responses, cancellation or interrupted execution can still leave an uncertain outcome. Do not automatically repeat an uncertain action. Historical receipts remain unchanged.

Review pending actions directly in their originating conversation. Pending cards remain at the end of chat even when the original activity is outside loaded history. Choose an explicit approval, edit, rejection or response on that card. A normal chat answer is not action approval. There is no Needs you page or separate decision queue. See [conversation questions and decisions](../notes/chat-interactions.md).

A decided action opens an Action receipt. Your decision and Execution outcome are separate sections. Outcome evidence appears first. Exact edited/reviewed payload is initially expanded; an edited decision also keeps Original proposal. Receipt details contains timestamps, turn/tool-call identifiers and review details. An older approval without a durable receipt is Unconfirmed. Its retained accepted edit is shown when available; otherwise an edited legacy decision identifies the original proposal and the missing accepted edit explicitly.

Unknown remains in history. Owner receipt inspection is required before a conflicting write; independent bounded reads and proven independent targets continue. Agent admission and model changes remain independent. Inspection never repeats an action or marks it successful. See [action outcomes](../notes/action-receipts.md).

A permission review shows the proposed filesystem boundary, selected session revision, workspace and extra roots before you decide. An unconfined proposal warns about host-readable credentials and destructive or remote effects. Acceptance covers one exact operation and does not change the session or future default. Receipts retain that recorded boundary even if the current mode later changes.
Approval review leads with the agent’s proposed action and target. Exact proposal opens expanded for ordinary tools; supported file comparisons remain above the decisions. Open Review details for the exact tool name, review version and source identifiers. Unknown tools keep their exact names. Avatar and reflection reviews retain their specialised previews with the exact proposal available. Integration input is labelled separately from a Question or Approval, in the conversation; responding keeps its existing permission meaning.


Accept approves the reviewed operation. Edit changes supported arguments and requires validation. Respond supplies a reply instead of executing; Ignore does not execute. Ask for context when unsure rather than assuming consent. Choose the current agent/conversation mode in the bot settings panel → Permissions, or type `/permission` in chat. Server settings changes only future-session defaults. Owner/Full access is required for changes.

Unattended turns normally may use only daemon-allowed read/search/browse operations; other actions are refused without asking unless the turn has explicit approval authority. Isolated turns have no tools. The handbook and status tools are reads and retain those restrictions. Human control of the computer also blocks bot input while active.

openag_capabilities is a read tool for selected first-party families. It reports environmental availability separately from the bot's effective permission mode and offline/unattended restrictions. Its result is an observation, not a grant: actual calls still check approval, cancellation, state and unresolved-action guards. Unknown tools keep their normal strict classification.

An integration can also request information during its running call. Open server requests appear in their chat, even when technical activity is hidden,. A Full access device or owner can answer, Decline or Cancel. This supplies input only; it does not approve another action, weaken permissions or confirm an external effect. Forms require explicit values and must not collect credentials. URL requests show their host and open only when you choose the link. Requests expire within two minutes, but the provider can cancel sooner. Enabled, configured push sends one response-needed alert per new request, subject to its rate cap. Answer in chat. They cannot resume after interruption or restart; no tool is replayed automatically. See docs/notes/mcp-lifecycle.md for supported forms, limits and privacy.

Task-only tools are unavailable with a reason in connection details. Invalid or unsupported catalogues/schemas are diagnosed before offering. When a tool contract changes, an old approval cannot execute the replacement. Returned structured data and errors are retained as bounded untrusted evidence, not proof that a write completed.

For the managed Composio connection, reviewed tool/skill search follows Search permissions; tool-schema retrieval and skill loading follow Read permissions. Other execution, connection/wait, proxy, shell/workbench, skill-change and feedback tools remain opaque operations requiring interactive Full access. A loaded skill grants no action authority. These declarations do not apply to similarly named tools on another server. Owner-selected session modes and independent turn ceilings remain authoritative.

The managed Composio connection validates its response envelope for every tool name before bounding output. Batch results must match the requested operations and explicitly report nested success; provider errors, malformed or missing results, and proxy HTTP failures report Failed. These checks apply to unfamiliar connector operations too. The reviewed read-only slug list controls permission only; it does not decide completion. Other MCP connections use the standard MCP error flag. Results and provider log references stay untrusted and redacted. See docs/notes/mcp.md for the shared result contract.


This release uses daemon-owned permission sessions consistently for API providers, Ollama and both ACP adapters. Read Only uses filesystem Read Only plus Ask; Workspace Write permits the bound workspace/approved roots plus Ask; Full access runs unconfined commands and uses Never. Full access may expose host-readable credentials and allow destructive or remote effects without individual prompts. Explicit review requests under Never are refused, never automatically accepted. Filesystem modes do not isolate reads, network or remote-account effects.

Fresh installs start in Workspace Write. Upgraded installs block tools until an owner reviews and explicitly adopts replacement modes in Server settings → Permissions. Compare the three mode choices, open Details → Previous rules to inspect the archive, then confirm the replacement and choose Apply mode. Full access also requires its separate risk acknowledgement. After adoption, the current default appears as a mode button beside Permissions. Open it to change the default for new conversations; existing sessions keep their mode. Old rules, including denials, are an immutable archive; they do not remain action authority after adoption. Adoption expires pending reviews and clears previous extra roots. It never replays actions, erases historical evidence or resolves Unknown. Limited devices can inspect modes but cannot change or adopt them.

Native ACP execution is disabled; use daemon tools. Native execution restrictions, including Codex's read-only setting, do not describe the boundary of OpenAg's daemon tools. For an authorized request, use the appropriate offered OpenAg tool and report its actual result; do not ask the owner to enable native execution just because that native setting is read-only. Respect daemon refusals. Unsupported host confinement refuses execution. Opaque MCP, Apps, computer input/shell and managed memory/skill writes require interactive Full access until their world supports confinement. Reviewed remote read contracts use daemon definitions, never server hints. A returned command exit does not confirm a downstream business effect. Use daemon read_file/list_files/search_files for bounded inspection; read timeouts do not block writes. Unknown blocks overlapping daemon-scoped paths across chats. Opaque shell/App/MCP writes remain conservative. Owner inspection preserves Unknown and invalidates only conflicting proposals. Restart preserves the guard. See docs/notes/daemon-execution.md.

A trusted session-level explanation distinguishes native and daemon execution.

A mode change expires pending reviews and cancels supported running execution; it cannot undo effects or clear Unknown. Cached ACP context is replaced on revision changes and reused within an unchanged revision. Delegation intersects parent and child authority; no writable mapping becomes Read Only, and a stale parent revision refuses dispatch. Full access still does not authorize background opaque execution, offline network calls, isolated tools or input during human takeover. Automatic receipts never imply human approval. See docs/notes/permission-sessions.md and docs/notes/permission-worlds.md for the execution contract and limits.

Permission choices show an eye for Read Only, a code shield for Workspace Write and a warning shield for Full access. The current mode uses the same icon in the bot panel and default-permissions controls; labels remain visible.

Local shell search includes `rg`.
