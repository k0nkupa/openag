# Computer and integrations

Use App library to discover integrations, review requirements and start setup. Added integrations link to their selected details in Settings, Connectors, which owns ongoing account and runtime management. The library's Manage connections link replaces its old Installed tab. Selected integration URLs survive refresh; old App library and Connectors list URLs remain valid. A configured or detected integration may still need access or setup.


Computer opens the managed-computer controls. The default backend is Cua; optional backends depend on administrator configuration. A configured backend is not proof a session is running. Shell availability varies by backend.

Computer actions share a lock. Human takeover pauses bot input while screenshots remain available. Computer shell is an external action. Clicking a submit button cannot reliably be detected from pixels, so input actions ask by default. Do not recommend making all input automatic as a way around action review.

Connectors and App library expose integration setup and installed capabilities. MCP servers are configured in the daemon data directory's mcp.json. The owner manages custom remote servers from Settings, Connectors; the MCP servers topic explains how. Enabled apps are owner-reviewed, integrity checked and run through the normal tool gate. A remote server's header may not reference the daemon's own secrets (its owner token, API keys or channel credentials); the administrator gives that server a separate variable of its own, and a server that refers to a protected one shows "header references a daemon secret". Credentials remain administrator-managed.

An integration may ask for your input again during a later call in the same conversation. Each response applies only to its own running call. OpenAg renews the capability handshake where the server does not retain an MCP session; it does not reconnect your provider account or replay a failed action. Keep provider permission controls enabled. Writes and unknown tools still require action review. See docs/notes/mcp-lifecycle.md for session and interaction behavior.

Available integration tools depend on actual installation and configuration. Handbook coverage does not mean a connector is installed, authenticated or working. Neither openag_help nor openag_status installs apps, launches computers, reads credentials, or performs integration actions. New capabilities and their external effects require the applicable authorization.

The capability catalogue reads a passive computer snapshot. It reports not_observed before the first observation, or the last observed lifecycle state with its timestamp. Busy, human_control and backend_switch_pending describe current local restrictions. Reading this catalogue never probes a backend, starts a computer, applies a pending backend switch or releases a hosted session. Shell support is backend-specific; screenshots remain separate from human input control. Configuration and permissions are reported separately, and execution rechecks them.


Apple apps, Gmail and Google Drive have read/search connector implementations. Apple uses a pinned local MCP facade (the pin identifies the reviewed code by digest; the daemon chooses how to launch it, so redeploying a new release or node does not require re-running setup); Gmail/Drive use one daemon-owned Google account with separate service pause controls. No send, edit, share or delete tools are offered by these connectors. Read tools still use the normal policy gate; offline turns cannot use Google reads. The capability catalogue currently covers search/computer/notifications, not integration account status.

A Connected card records connection state; Check read access is explicit and adds a timestamp, not proof that every item works. Apple permission prompts and read checks are separate. Apple permission badges show Granted in green, Not checked in amber, and Not granted or Check failed in red. All App library integrations share a details dialog: Overview contains connection actions, with source/version and diagnostics under Connection details, Tools contains expandable tool descriptions, and Setup appears when a reviewed recipe is available. Status is shown once beside the integration name. In Apple apps, Overview lists the seven apps; expand an app row for Request permission and Check read access. Connection details contains runtime diagnostics and requirements; Tools contains the tool list. Setup contains the reviewed setup and disable commands. The last Request permission result per app is saved in the data folder (`apple-permissions.json`, owner-only) and survives daemon restarts and redeploys; it is a record of the last check, not a live macOS query, and Read verified resets on restart until Check read access is run again. A failed runtime can coexist with granted macOS permission; read checks remain disabled until the runtime connects. Google sign-in requires a Full access device; provider credentials stay in daemon configuration. Disconnect Google removes both Gmail and Drive access, while pausing affects one service. See docs/notes/read-connectors.md for authoritative setup, scopes, privacy, supported formats, recovery and backup limits. Real apps/accounts and background-service acceptance remain unverified (OA-354); implementation and controlled checks do not prove those work on the installed host.


Calendar reads use native EventKit and require Calendar Full Access. Reminders list/search also use native EventKit and require Reminders Full Access on the daemon host. This macOS permission permits both reads and writes at the OS level, but OpenAg exposes only read/search operations. Ask for access is explicit; opening a card or calling a read tool does not request Full Access automatically. See docs/notes/read-connectors.md for the build requirements and bounded upcoming-event window.

Composio supports browser sign-in from its App library connection without a Composio API key. A Full access device is required. OpenAg generates and preserves its connector encryption key automatically; users do not enter keys. A damaged connector record does not disable another saved connection during key import. Desk and callback addresses are separate. Use Connect in Setup (or Reconnect on Overview in Connectors for an existing account), sign in in the new tab, and the original desk checks the result; there is no address-entry section. The daemon sets up a private Tailscale callback automatically; a hosted callback relay is used only when the operator has configured one (`OPENAG_SIGNIN_RELAY_URL`). Without Tailscale or a configured relay, browser sign-in is unavailable. The server completes the device-bound attempt. The hosted relay receives a short-lived code/state response and stores only an encrypted callback for the daemon; it does not receive owner/device credentials, the private verifier, provider tokens or tool data. Existing Serve routes are preserved and public Funnel is never enabled. Route availability, deployment and real consent must be checked separately. Cancel sign-in preserves an existing connection. Existing keys and registrations are preserved; missing original key state requires recovery, never silent replacement. Connecting Composio and granting access to another service are separate steps. Reviewed tool/skill discovery, schema retrieval and skill loading use explicit daemon read contracts. Other opaque execution requires interactive Full access, while explicit operation review under Never is refused. Unconfirmed external actions retain Unknown receipts. Disconnect uses a red outline button and asks for confirmation. It removes local access; provider revocation is unconfirmed. Existing API-key bridges are preserved as legacy installations. See docs/composio.md for authoritative setup, privacy, recovery and limitations. Source and controlled checks do not establish deployment or live-provider acceptance.


MCP tools use the same classification and receipt rules across integrations. Administrator-reviewed discovery/read tools can follow normal read/search permissions. Opaque tools require interactive Full access; unknown operation requirements request review and Never refuses them. Discovery results are evidence about available tools and connections; they do not prove mailbox access or approve later actions. See Approvals and permissions for returned results with unconfirmed effects.

Remote integrations can request explicit form or URL input during a call. Review these directly in the originating conversation. Integration Overview reports task-only or unsupported-schema tools as unavailable. See Approvals and permissions and docs/notes/mcp-lifecycle.md; connecting, supplying input and approving an action remain separate.

Computer has Refresh status in the full page and conversation panel. Unknown or unreadable status requires another status check and, if unresolved, inspection on the OpenAg machine. It is not evidence that the computer is absent. Refresh never creates, destroys or switches the computer, or releases a hosted session. An explicit backend selection is separate; if busy or human control blocks it, wait and use Apply selected backend. See [status inspection and recovery](../notes/cua.md).

Integration input requests use shared labelled fields and checkbox groups for multiple choices. Optional values remain unset until selected; Yes and No are distinct choices. Responding remains separate from tool approval. See `docs/notes/mcp-lifecycle.md`.

Slack setup is in Connectors. Its connection badge reports state separately from the Enable Slack setting. Room/channel fields and the allowed-user list remain explicit; Server setup and Connection activity expand for credential setup guidance and counters. Saving still requires Full access and never grants tool approval. See [Slack behaviour](../notes/slack.md).

Local setup follows requirements, package/access review, acknowledgement, an owner-run terminal command, then an explicit Reload and check installation (App) or Reconnect and check installation (MCP). Package details and rollback stay expandable. A changed package, target or command clears acknowledgement. A failed status read never reports installation success. Detected Apps still require a separate Review and enable action in Connectors. See docs/notes/desk-integrations-ux.md.

Disconnect opens a confirmation with Keep connection focused first. Gmail and Drive share a Google account: disconnect removes both; Pause this service affects only the selected service. Composio disconnect removes local access; provider grant revocation remains separate. Return to connection after sign-in reopens that integration, using current status to choose setup or management. Google keeps the selected Gmail/Drive service name only for this browser session; if unavailable, it returns to Gmail.

Refresh status reads the shared inventory without reloading integrations or contacting a provider. Reload app folders and Reconnect MCP are under Advanced maintenance; MCP reconnect affects all configured servers. Integration cards/details show a next step from the known state; Connection details keeps exact sanitized diagnostics and requirements. A failed status read shows the last snapshot as Status unavailable and blocks account actions and review acknowledgement. Action success appears only after status readback; a lost readback never retries the action. Restore connectivity and use Refresh status to inspect what happened.

A Limited device can browse library status but cannot manage Google account details. Its account view asks for a Full access device; this is an access restriction, not a connection outage. Failed initial reads stop the loading state and do not claim a previous snapshot exists.
