# Backend-managed OAuth onboarding: OpenBot and CopilotKit

Historical research before OA-365 (formerly OA-363). Its OpenAg setup findings describe the pinned baseline below; current implemented behavior and verification are in [managed onboarding](managed-onboarding-verification.md).

Checked 2 November 2026 using current primary source files retrieved through the GitHub API. Research only: no OSS app was installed or run, no tests or sign-in were performed, and OpenAg code, service configuration and accounts were not changed. Prior connector research notes remain intact.

## Finding

The requested user experience is supported by concrete source examples: **the application or its launcher can own encryption-key generation, persistence and callback plumbing, leaving the person to click Connect and consent.** CopilotKit/OpenBot's desktop launcher is an especially direct example: its source explicitly says it prepares configuration for somebody who will never open a terminal and generates a real encryption key. However, the statement that these projects eliminate all key/URL setup is too broad. Their raw server deployments can still require operator configuration, and their checked Composio integrations still use a Composio API key. [Desktop launcher](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/desktop/src-tauri/src/env.rs#L1-L16), [server key requirement](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/config.ts#L493-L530), [Nightly Composio manifest](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/marketplace/plugin-catalog/plugins/composio/plugin.json), [CopilotKit OpenBot Composio responsibilities](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/docs/plugins/composio.md#L1-L35).

## Nightly OpenBot: what it actually automates

**Storage.** `application-services.ts` constructs a cipher using `safeStorage.isEncryptionAvailable()`, `encryptString()` and `decryptString()`, then passes it to `McpOAuthStore` at `app.getPath("userData")/openbot-mcp-oauth-v1.json`. The store persists encrypted per-server registrations/tokens, and preserves unreadable ciphertext rather than treating a transient keychain failure as an empty vault. This uses OS-backed encryption; it is not evidence that encryption is unnecessary or that a Node daemon automatically has Electron's vault. [N1: cipher and wiring](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/main/application-services.ts#L649-L659), [store construction](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/main/application-services.ts#L1371-L1386), [store implementation](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/main/mcp-oauth-store.ts).

**Callback.** The application starts its own listener and obtains `http://127.0.0.1:<actual-port>/mcp-auth`; it tries port 28417 and can fall back to another free port. The returned URL is passed into `McpOAuth`; failure to bind falls back to the `openbot://mcp-auth` deep-link path. The OAuth provider registers its current redirect URI, detects stale registrations and uses the MCP SDK for discovery, registration, PKCE and authorization. Its refresh path is deliberately separate from an interactive authorization flow so background refresh does not silently register a new client. [N2: listener](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/main/mcp-oauth-redirect-server.ts#L1-L86), [startup wiring](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/main/application-services.ts#L1419-L1451), [OAuth implementation](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/backend/mcp-oauth-provider.ts#L359-L409), [client metadata and registration](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/src/backend/mcp-oauth-provider.ts#L842-L937).

**Remote use has a real transport design.** The documented `sign-in-relay-v1` Team API flow starts OAuth on the executing host, opens the page on the user's computer, receives a loopback callback on that computer, then posts the callback query to the host. The host retains the grant. This is a joined client/host relay, not evidence that every generic browser has a loopback listener or that a hosted callback broker is required. The browser client cannot bind that local native listener and the documented fallback asks the user to paste the final address. A phone-only OpenAg browser therefore cannot simply reuse the desktop loopback mechanism unchanged. [N3: sequence](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/docs/architecture/integrations.md#L101-L145), [client fallback](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/docs/architecture/integrations.md#L162-L178).

**Its current Composio listing is not proof of keyless Composio OAuth.** The manifest uses `kind: "key"`, with fields for an MCP URL and an API key sent in `x-consumer-api-key`. The placeholder URL happens to be `https://connect.composio.dev/mcp`; the auth selection is still explicit consumer-key auth. The generic OAuth machinery above and this particular marketplace listing are separate facts. [N4: exact manifest](https://github.com/nightly-labs/openbot/blob/ac99196e66fe8f9d426433aa5e79d6e999d1c818/marketplace/plugin-catalog/plugins/composio/plugin.json#L1-L52).

## CopilotKit: framework versus application

**Core SDK.** `MCPClientConfigHTTP` accepts Streamable HTTP transport options, including a wrapped fetch; SSE accepts headers. `mcpClients` lets an application supply clients whose configuration and lifecycle it owns. The runtime constructs an SDK transport from supplied options and closes the clients it creates. This is useful integration plumbing, not evidence of a product-level generated encryption key, callback-origin selection or hosted connector account service. [K1: interfaces](https://github.com/CopilotKit/CopilotKit/blob/c5616c818bf9b6d97b29fb1d766876c807e2b208/packages/runtime/src/agent/index.ts#L160-L214), [transport construction](https://github.com/CopilotKit/CopilotKit/blob/c5616c818bf9b6d97b29fb1d766876c807e2b208/packages/runtime/src/agent/index.ts#L1741-L1785), [cleanup](https://github.com/CopilotKit/CopilotKit/blob/c5616c818bf9b6d97b29fb1d766876c807e2b208/packages/runtime/src/agent/index.ts#L2341-L2355).

**CopilotKit/OpenBot desktop supplies the missing product layer.** Its launcher generates 32 random bytes in base64, includes `KEY_ENCRYPTION_KEY` among secrets minted once per deployment, and keeps a usable existing value instead of replacing it on every start. Source explicitly identifies changing this key as a data-loss risk. Its vault currently uses an owner-only file on macOS/Linux and Windows DPAPI; do not incorrectly describe all these platforms as OS-keychain encrypted. This is a direct model for removing manual key provisioning from OpenAg's normal installation. [A1: purpose](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/desktop/src-tauri/src/env.rs#L1-L16), [random generation](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/desktop/src-tauri/src/env.rs#L384-L395), [reuse before generation](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/desktop/src-tauri/src/env.rs#L605-L631), [vault platform behavior](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/desktop/src-tauri/src/vault.rs#L1-L13).

**Server deployment still has operator requirements.** `loadConfig()` calls `keyEncryptionKey()`, which requires `KEY_ENCRYPTION_KEY`, validates a 32-byte base64 value and refuses the public example value in production. Helm likewise requires a configured key or an existing/external secret. Automatic desktop installation and a manually operated server are different setup surfaces. [A2: validation](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/config.ts#L493-L530), [config assembly](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/config.ts#L1407-L1433), [Helm secret](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/charts/openbot/templates/secret.yaml#L1-L25).

**Callbacks use a shared app-level address.** `redirectUriFor(publicUrl)` appends `/api/plugins/oauth/callback`. Its comment expressly rejects building this from untrusted request headers. Configuration uses `OPENBOT_PUBLIC_URL`, otherwise the existing authentication base URL; the `.env.example` says most installations therefore never set the extra variable. `OPENBOT_APP_URL` separately selects the browser application's return origin. The server handles callback exchange and encrypted state. Dynamic registration exists for catalogue entries/providers that support it; this does not mean every provider supports registration or needs no operator-created OAuth client. [A3: callback derivation](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/plugins/oauth.ts#L86-L107), [URL defaults](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/config.ts#L1407-L1448), [documented setup](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/.env.example#L100-L113), [registration](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/plugins/oauth.ts#L449-L485), [callback handler](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/plugins/route-groups/oauth-callback.ts#L32-L108).

**Composio remains a brokered, operator-key path.** The project documentation separates the deployer's `COMPOSIO_API_KEY`, administrator app enablement and per-Bot grants, and each person's account consent. It says there is no per-service client secret or redirect URI for the person because Composio holds the upstream account. It also explicitly says Composio is unavailable until the deployment key is supplied. This illustrates backend-owned setup and clear responsibility boundaries; it does not implement the same keyless Composio-MCP sign-in selected for OpenAg. [A4: responsibilities and key behavior](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/docs/plugins/composio.md#L1-L53), [config field](https://github.com/CopilotKit/OpenBot/blob/c396a5f68c817043846f1ca3c2b42061ee73ceb5/server/src/config.ts#L1435-L1447).

## Smallest OpenAg recommendation (inference, not implemented)

1. **Own the local storage key in the daemon/installer.** Retain an explicitly supplied `OPENAG_CONNECTOR_KEY` as an override. With no existing credential/key needing recovery, generate a cryptographic key once, persist it privately under the owned data directory and reuse it across restarts. Preserve existing Google credentials and their key; never silently generate a replacement merely because an old key is missing. This follows the desktop launcher's reuse-before-generation pattern rather than removing encryption. [A1]
2. **Make the callback an application-level concern.** OpenAg currently has no established general public-app URL setting; adding one trusted app address, or a validated installation-time address selection, is real work. Derive the fixed Composio callback path from that address and keep it out of ordinary connector onboarding. Avoid trusting arbitrary Host/forwarded headers. For a phone browser, the URL must reach the same daemon and satisfy the provider's callback policy. The Nightly native loopback relay cannot be assumed to exist in a plain mobile browser. [A3][N3]
3. **Keep the existing OAuth machinery and simplify the visible flow.** OpenAg already has SDK registration/PKCE, daemon-owned refresh/storage and its policy gate. Remove the avoidable per-connector environment-variable wall; show Connect, provider consent, Connected, Reconnect and Disconnect. Keep specific setup failures visible when an address or existing encrypted store genuinely needs administrator repair. This is a product-onboarding correction, not a reason to adopt CopilotKit or replace the existing agent runtime. [K1][A1][A3]
4. **Keep Composio paths explicit.** The reviewed OSS examples use different Composio auth arrangements. They support borrowing backend setup patterns; they do not prove that changing OpenAg to a consumer API key or REST broker key would satisfy the requested keyless user sign-in. Verify the chosen shared-MCP OAuth path end to end separately. [N4][A4]

The local OpenAg findings above were checked against `apps/daemon/src/composio-connect.ts` and `connector-credentials.ts`: configured state currently requires both environment settings, and the store has no generation path. [OpenAg OAuth configuration](../../apps/daemon/src/composio-connect.ts), [credential store](../../apps/daemon/src/connector-credentials.ts). No implementation or live OAuth acceptance is claimed here.

## Limits and reuse

This is a selected-source review, not a complete security audit or runtime/provider acceptance. Actual Composio callback registration policy for OpenAg's phone-accessible address, durable daemon key recovery/backup behavior and a complete phone-browser sign-in remain unverified. The exact checked projects should not be summarized as “all setup is automatic” without naming the deployment surface.
