# Permission sessions and automatic action evidence

Status: implemented from OA-402 and included in the local `0302874` release deployed on 5 November 2026. This is a dated local installation record, not a claim about other installations or live provider acceptance. See release evidence. Fresh databases use Workspace Write; upgraded databases refuse tools until explicit owner adoption. Earlier checkpoint evidence below is historical.

## One persistent selection

`permissions.ts` owns a session for each bot and room. Inspection is passive: an unstarted session reports its proposed default with revision zero and no bound workspace. The first actual turn or an explicit owner selection creates the session. Its id and canonical workspace survive daemon restarts and ACP session changes. A new session copies the standing default once; subsequent default changes do not change existing sessions. Presets are Read Only / Ask, Workspace Write / Ask and Full access / Never. Clients cannot supply another pair. Explicit roots are canonical absolute directories and remain owner-controlled.

The scoped gateway exposes authenticated session/default reads and owner-only changes. Changes require the current revision. Full access requires an explicit acknowledgement in the request. A change increments the revision, records configuration evidence and expires pending requests for that bot and room. A stale request cannot broaden authority. Limited devices cannot select a preset. Mode authority is separate from provider consent and device access.

The runner gives registered tools a trusted execution requirement and boundary. Missing requirements request review; Never refuses review rather than automatically accepting it. The permission service is mandatory at invocation. The production entry point supplies it; no category fallback remains. Turn isolation, unattended restrictions, cancellation, validation, ownership and uncertainty guards remain separate ceilings.

## Communicating effective permissions

Each ordinary Claude/Codex turn receives the effective OpenAg permission context, even when its ACP session is reused. Guidance distinguishes daemon tool execution from disabled native execution: the native read-only setting is not the filesystem boundary of `run_shell`, `write_file` or managed writers. The bot should use the appropriate offered tool for an authorized request and report actual refusals/results instead of assuming it needs a native sandbox change. This context grants no new authority and does not override independent restrictions. See [ACP execution](acp.md#effective-permissions-and-native-execution) for the runtime guidance contract.

ACP adds a static trusted explanation through supported append-only session instructions, while effective policy remains current per turn. Stored bridge versions prevent reuse of legacy instruction contexts. Matching resumes resend the same bridge; failed resumes stop instead of silently starting fresh. This does not change native permissions or grant daemon actions. See [trusted session instructions](acp.md#trusted-session-instructions-oa-464-source).

## Exact escalation and dispatch

The new daemon command tool normally runs inside the selected boundary. `escalation.reason` proposes one exact unconfined command under Ask. It does not edit the session, grant standing extra roots or automatically retry a failed command. The command is not editable in an approval; a changed operation requires a new proposal. Under Never, that explicit request is refused with no pending approval.

The gate records the permission id/revision with a reviewed proposal. Dispatch rechecks the revision and trusted tool requirement. A delayed executor must call its trusted dispatch assertion after asynchronous preparation and before the effect; the command executor does so immediately before spawning. Canonical workspace/root aliases are rechecked. A changed revision refuses the stale call even when the new mode is broader. Running operations are not described as undone by changing the mode.

## Independent operation receipts

The receipt schema preserves historical ids, ordering, proposals, decisions, evidence and inspection records. Each operation now has an independent id. Human-reviewed operations keep their genuine approval reference; automatic operations store `approvalId: null` and `decision: automatic`. No synthetic approval is created. The receipt retains the selected mode/revision and effective command boundary, including a scoped override.

Unknown outcomes remain historical evidence. Only conflicting daemon-owned scopes block a new write; opaque/historical unscoped actions remain conservative. Owner inspection preserves evidence and invalidates conflicting proposals only. Model settings and agent requests do not themselves repeat an action. No action is automatically replayed.

Pending permission reviews display the proposed filesystem boundary, selected preset/revision, workspace and extra roots. Unconfined proposals explain credential and remote-effect risks before a decision. Acceptance covers exactly one operation and leaves session/default selections unchanged. The actual receipt page handles both human and automatic records, shows the execution evidence and original permission snapshot as structured fields and retained JSON, with the owner inspection form for uninspected Unknown outcomes. Activity links use receipt ids; Unknown automatic actions remain in history rather than Recovery. Existing approval detail URLs remain compatible and may return `approval: null` alongside an automatic receipt.

## Controls and lifecycle

The bot settings panel → Permissions shows its mode for the current conversation. The composer has no permission row. The `/permission` picker can select another member in a shared room. `/permission` opens the same picker locally and never reaches a model. Full access requires a fresh explicit acknowledgement. Limited devices can inspect but cannot save. Server settings has a separate default picker; this affects only sessions created later. Extra roots and host confinement support are visible. Concurrent edits retain their opening revision and receive a conflict rather than overwriting another device's change. Stream reconnect/config events refresh observations.

A session revision change expires pending requests and cancels affected active turns, including delegated descendants. The daemon signals supported commands and adapters to stop; continuing or uncertain effects remain honestly recorded, and cancellation does not resolve Unknown receipts. The next ACP turn discards cached context from another revision. Calls within an unchanged revision still reuse their adapter session. Restored sessions cannot load an old ACP id across a changed permission context. Changing a standing default leaves existing contexts intact. These controls are wired into the source release; upgraded installs require the explicit adoption described below.

OA-401 controlled desk/gateway checks and the disposable active-command cancellation journey passed. Both real ACP adapters reused unchanged Workspace Write and Full access contexts, and replaced context after each mode revision. IAB inspection covered desktop 1280×720 and mobile 390×844, keyboard focus/scroll, the named acknowledgement and Escape focus return. The temporary preview was closed and its server stopped. Sanitized evidence: [permission-controls.json](permission-modes/permission-controls.json). These are source/temporary-data checks, not installed-device or deployment acceptance.
