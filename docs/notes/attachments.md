# OA-315 input attachments

Verified locally on 1 November 2026 in `codex/desk-shell`. These are user inputs, separate from OA-322 saved results.

## Contract

Authenticated POST `/rooms/:id/uploads` takes raw bytes, a supported Content-Type and a URI-encoded `x-file-name`; it returns an opaque UUID and display metadata. GET/DELETE `/rooms/:id/uploads/:uploadId` require device authentication and a public room. DELETE only removes unbound draft uploads. POST messages takes `text` and optional `attachments: UUID[]`; binding and message publication share one SQLite transaction. IDs cannot cross rooms, be duplicated or be reused by another message. An unconfirmed send retains the draft; a second submission of already-bound IDs is refused instead of duplicating it.

Limits: six files / 10 MiB per message; 5 MiB per file; UTF-8 text, Markdown, CSV and JSON capped at 64 KiB each after redaction; PNG/JPEG capped at 20 million pixels / 16,384 per dimension. Empty, binary text, invalid headers/dimensions, unsafe display names and other MIME types are refused. Image headers/dimensions are checked, not fully decoded or virus-scanned. Generated UUID filenames live in `$OPENAG_DATA/uploads/<hex room ID>/`, with mode 600 and no-follow reads. Paths never enter bot prompts. Text and names use the existing redactor before persistence. Failed writes are removed. Binary images cannot undergo text-secret redaction.

Unbound uploads are capped globally at 32 files / 100 MiB. Uploads older than 24 hours are pruned on the next upload; this is bounded lazy cleanup, not a new background service. The composer cleans up known unbound files when removed or unmounted, except while a message send is in flight (it may still bind them). Unknown network outcomes remain bounded by that quota/expiry. Bound inputs remain available with their message. Send waits for uploads and removals; Retry has a per-row in-flight guard.

ACP uses advertised prompt capabilities: text resources with `embeddedContext`, image blocks with `image`. Adapters without resource support receive bounded redacted inline text; adapters without image support receive the filename and an explicit unavailable-content notice. This compatibility fallback qualifies the ticket's resource wording. API models receive text plus image bytes when the shared cached catalogue reports image support; unknown capability receives image names only. Model-family names are not used as a vision allowlist. Ollama checks `/api/show` capabilities before including images. No model-account readiness is inferred from a model name. Capability sources: [ACP schema](https://agentclientprotocol.com/protocol/schema), [OpenAI image inputs](https://developers.openai.com/api/docs/guides/images-vision), [Claude vision](https://platform.claude.com/docs/en/build-with-claude/vision), [Ollama OpenAPI](https://github.com/ollama/ollama/blob/main/docs/openapi.yaml).

The composer supports attach, thread drop and image paste through one upload path, per-file errors, image previews and removal. File chips download through authenticated fetch; visible image chips load previews lazily. Failed send keeps text and files. The current WebRTC transport carries bounded text frames only: it explicitly refuses attachment operations with a LAN/Tailscale message instead of returning corrupted binary data. Binary RTC framing remains outside this ticket.
