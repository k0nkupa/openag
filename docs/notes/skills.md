# Skills (OA-204, OA-384)

A skill is a reviewed reusable method. A skill package contains its instructions and resources; discovery, assignment, readiness and action approval are separate facts. Facts belong in MEMORY. This guide describes source behavior, not deployment or real workflow success.

## Stores and ownership

Agent-owned skills remain `$OPENAG_DATA/bots/<botId>/skills/<slug>/SKILL.md`, versioned through datagit. Managed path handling is centralized in `skills.ts`; symlinks at any managed path level are refused. `skill_save` writes only here, bumps a positive numeric version and commits through `commitMemory`. Reflection proposes agent-owned skills and only accepted/validly edited Inbox proposals are applied. Shared discovery grants no write authority.

The optional shared library is the daemon user's `~/.agents/skills`. It starts disabled and is enabled by an owner/Full device in the agent’s conversation side panel → Settings → Knows → Skills. It cannot be relocated through HTTP or tools. The injected constructor root is solely a trusted daemon/acceptance seam. Discovery reads existing packages; it creates no directory, installs nothing and never executes scripts.

## Catalogue, assignment and loading

`createSkillCatalogue` owns discovery, identities, assignment checks, bounded indexes and resource reads. Normal agent reads inspect only that agent's managed and assigned packages; full shared discovery is reserved for owner inventory requests. The main daemon shares one instance with the runner, gateway and first-party tools. Source enablement and per-agent assignments persist in the existing settings table (`skillLibrary`). New shared packages are unassigned. Secret-bearing identities are hidden; explicit configuration writes remove stale private identities across all assignments without mutating state during passive reads. Agent-owned skills remain available without a shared assignment.

Identities are `agent:<botId>:<slug>` and `shared:<relative-package-location>`. Same-name packages stay distinct; nothing is merged and missing assignments never rebind by name. Legacy managed slugs still load. The prompt index is capped at 40 entries/2,000 characters. `skill_list({query?,offset?})` returns up to 20 entries belonging to the requesting agent, including availability reasons and a next offset; tool arguments cannot supply another agent's identity.

`skill_load({slug,path?})` accepts a source-qualified id as slug. Without path it loads instructions, metadata and a bounded list of resources. With path it reads one UTF-8 reference inside an assigned shared package. Unknown/unassigned/disabled/unsafe inputs return `found:false`. Decoded YAML metadata and reference text are redacted, secret-bearing resource names are omitted/refused, and results are marked untrusted and carry an instruction-priority notice. Both tools are read-class and pass through the existing policy gate; unattended and isolated restrictions are unchanged.

Managed reading and writing retain their existing literal line format, including hash characters and numeric trigger text; there is no managed-format migration. Portable shared packages use YAML frontmatter with required string name/description and no mandatory version. Multiline descriptions work. Shared descriptions allow 1,024 characters; names allow 80 for compatibility with existing authored skills. Managed writes retain their version, literal metadata and comma-separated triggers. Shared compatibility text is displayed as unverified requirements, not a dependency probe or a readiness guarantee. Tool metadata such as allowed-tools grants no permissions. Client-specific invocation flags and agents/openai.yaml are not interpreted; assignment controls availability and the model chooses when to load a workflow.

## Filesystem and size limits

Shared discovery supports grouped directories and skill-directory links under the owner-enabled source. Such links deliberately trust their resolved package directory. Broken links and cycles are ignored; SKILL.md must be a regular non-symlink file. Reference targets must remain inside that resolved package. Only inventoried regular, non-hidden resource files are readable. Absolute paths, traversal and links escaping the package are refused. Managed write-path symlink restrictions are unchanged.

Reads reject non-regular entries before opening with nonblocking/no-follow flags, are bounded to 64 KiB, checked again on the opened regular file, and decoded as UTF-8; binary resources return unavailable through this route. Instructions are capped at 16 KiB. Resource inventory lists at most 100 files with bounded depth and traversal; shared discovery visits at most 400 directories, six levels deep and 200 children per directory, bounded during enumeration rather than after materializing the directory. Managed scanning retains its 200-entry limit. Unassigned packages beyond discovery limits are not inventoried; existing assignments are checked directly. Library reads are bounded and do not promise exhaustive indexing. Scripts/assets are identified, not executed or automatically installed. Reads still have a same-user filesystem race between canonical path checks and opening a file; these checks are not an OS sandbox.

## Gateway and desk

All routes require normal authentication. `GET /skills/library` reports enablement; owner-only `PUT /skills/library` accepts enabled only. Owner-only `GET /skills?botId=...` inventories packages for assignment, and `GET /skills/package?botId=...&id=...` previews instructions before assignment. Owner-only `PUT /bots/:id/skills/assignments` accepts an ids array. Existing GET bot skills routes return assigned and agent-owned packages; a path query on the individual route reads a permitted UTF-8 reference. Generic PUT settings cannot replace the skill library configuration or bypass assignment validation. Configuration is validated and audited without package contents; the skills top-level segment is reserved from static serving.

The Skills sheet uses a compact global-library switch, a searchable list with source identities and immediate assignment switches, and a focused preview with All skills navigation. Assignment saves retain the open preview; failed writes or readbacks keep mutation controls locked until a successful refresh. Package details discloses requirements/resources and About skills holds permission guidance. Keyboard navigation remains instant; Back returns focus to search. Limited devices can inspect their existing skill views but cannot change enablement or assignments. A failed mutation requires a refresh/readback before another attempt. Shared package contents never enter the managed save or reflection path.

## Installing an external agent-owned package

Use `skill_save` for the complete instruction body and metadata first. Summarize source descriptions longer than the managed 200-character input limit; do not truncate the instruction body. It creates the managed directory, redacts the instructions and writes a versioned `SKILL.md`; a source package without a managed version is not recognized by a raw unchanged copy. Required references/assets can then be copied into the resulting directory through independently authorized daemon tools. That copy is not an activation of plugin MCP connections or scripts. Confirm catalogue listing and instruction loading, then read an installed reference through an authorized filesystem tool. The `skill_load` path option applies to assigned shared packages, not agent-owned resources; an empty managed resource projection does not make authorized filesystem reads unavailable. Missing target directories before the managed save are expected rather than proof of a permission denial.

Disposable acceptance must preserve the complete instruction body, adapt metadata to the managed schema, preserve reference bytes and the source package, and observe actual reference reads after reuse/resume. A copied folder, a remembered answer or a managed instruction file without its required bundle is insufficient. This section describes the existing tools' composition; it adds no generic directory importer or new action permission.

## Runtime context and changes

Claude ACP sessions use `settingSources:[]` and an explicit empty native `skills` allowlist. Codex ACP configuration forces `skills.include_instructions:false`, `skills.bundled.enabled:false` and `features.skill_search:false`, preserving other operator configuration. On the installed Codex 0.164.0, the skip_host_skill_discovery flag alone did not remove the synthetic skill from the outgoing model request, so it is not used as proof of suppression. Installed SDK controls and real adapter request inspection are recorded in the acceptance note; upstream context: [Codex configuration schema](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json).

Assignment/source changes invalidate cached ACP sessions. Persisted resumed turns discard their saved ACP session id when skill configuration differs. Instructions already delivered remain historical context; no removal can erase them or create new action authority. Shared assignments select a package rather than a pinned revision. External edits affect later loads and are revalidated; per-revision review and pinning are not implemented. Runtime upgrades need fresh native-catalogue verification. Independent authorized file/shell access remains possible.

## Verification

`node scripts/verify-shared-skills.mjs` exercises a temporary gateway and actual runner/API runtime plus controlled ACP/MCP. It checks assignment isolation, package/reference reads, duplicate names, scope refusals, approvals, reflection, shared byte preservation, missing/changed packages, directory links, pagination and restart persistence.

`node scripts/verify-native-skill-discovery.mjs` launches the installed real ACP adapters with synthetic homes and loopback model endpoints, inspects outgoing requests and closes the turn. It checks catalogue suppression, not real model quality or external-provider acceptance. `node scripts/verify-bot-knowledge.mjs` checks packaged handbook delivery. UI and final review evidence belongs in `shared-skills-acceptance.md`. No unit/Jest/Vitest runner or deployment is authorized by these checks.

Successful shared-package reference reads return the canonical source-qualified package id, its known version (or null), the permitted relative path and redacted text. Request provenance retains that source metadata and a content digest, not the reference body.

Managed saves declare the package directory and shared serialized Git history as their effect scope; independent workspace writes can continue after a scoped skill uncertainty, while overlapping package/history writes still require owner inspection. This does not narrow opaque shell actions. See [daemon execution](daemon-execution.md#bounded-inspection-and-conflict-scope).
