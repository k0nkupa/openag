### Requested, acknowledged and returned identity

Keep these evidence levels separate:

1. **Requested/effective input:** the selected stored configuration after environment precedence, plus the exact validated options submitted to the runtime. This is configuration evidence.
2. **Acknowledged configuration:** a runtime acknowledgement of a selection, where that runtime offers one. A successful hosted response implies the request was accepted, but is not an independent echo of every option.
3. **Returned model identity:** the provider's `response.model` / Ollama top-level `model`. This is the service's report of the serving model, not an inference from the bot's settings. A provider can still return an alias; retain exactly what was reported rather than inventing a canonical version.
4. **Returned reasoning state:** use an explicitly reported effort/configuration field only where the response contract supplies it. A trace or nonzero reasoning-token count proves neither the named effort nor the exact option mapping.

Mastra's installed output types expose `response.modelId`, `providerMetadata`, warnings and per-step results. The bundled OpenAI Responses, Anthropic Messages and OpenRouter implementations populate `response.modelId` from the upstream `response.model` (bundle lines 9857, 15064 and 19427 respectively). OpenRouter also reports the routed provider in `providerMetadata.openrouter.provider`. Keep per-step model provenance if a multi-step run reports different values; never fall back to `Agent`'s configured model ID and label it returned evidence. Installed sources: `dist/stream/base/output.d.ts`, `dist/stream/types.d.ts` and `dist/netlify-k1oRkpJD.js`.

OpenRouter reasoning metadata contains reasoning detail blocks and token counts; these are not an effective effort echo. Anthropic effort documentation describes a request parameter; its model/usage response is not an effort acknowledgement. OpenAI Responses can expose response-level reasoning configuration in the upstream body; the usable shape and preservation through the selected Mastra transport must be checked in controlled acceptance before relying on it. Never store raw response bodies, prompts, headers or reasoning traces merely to obtain a model/effort label: select minimal typed metadata and apply existing redaction.

Ollama `/api/chat` returns top-level `model`, `message.content`, optional `message.thinking` and timing/token counters. The documented response does not provide an independent `think` value echo. Report the request/default with its provenance and leave independently reported effort unknown. Existing `chat()` returns only `{message}` and therefore loses even the returned model field. `cleanReply` removes legacy `<think>` text, but presence of that text cannot establish a thinking configuration. [Ollama chat API](https://docs.ollama.com/api/chat), [thinking](https://docs.ollama.com/capabilities/thinking); [ollama.ts](../../apps/daemon/src/runtimes/ollama.ts).

### Planning constraints and remaining verification

- Keep hosted provider choices within the existing OpenAI/Anthropic/OpenRouter paths. Mastra's broad registry does not authorize new provider integrations, custom endpoint forms, credential management or automatic model fallbacks.
- A catalogue-backed selector and provider-account discovery answer different questions. Planning must decide how to show eligible, configured, unsupported and unknown states without starting inference on sheet open or save. Model-list reads need bounded pagination, timeout, fixed hosts and safe errors; no credential value should reach a form or audit record.
- Treat configuration, environment override, selected session configuration and last returned model as separate facts. Explicit unknown/stale labels are necessary where reasoning state is not independently reported. In particular, a universal “effective effort” guarantee across all providers is not supported by the researched response contracts.
- Reuse `ctx.callTool`; model configuration must not introduce another approval engine or bypass it. No configuration save should start a turn. Hosted/Ollama request and output metadata checks can use controlled responses without units/Jest/Vitest; real provider acceptance still requires separate applicable authority.
- Local Ollama server version, installed models, thinking metadata and inference were **not** queried. Current upstream thinking discovery may be absent on older servers; detect the actual response and show unknown/unavailable rather than applying a hardcoded fallback.
- No account-specific OpenAI/Anthropic/OpenRouter model list, key presence, billing state, model call, tool call or provider-side reasoning acknowledgement was checked. No new dependencies are indicated by this research. Public docs were fetched on the research date; installed package source is the version-specific evidence where docs and local behavior may differ.

The response carries the complete updated options; agent-originated `config_option_update` notifications also carry the complete list. Model changes can alter the supported effort choices. ### Claude adapter 0.97.0

- Discovery is session-based. The adapter obtains models from Claude SDK initialization, applies provider/managed restrictions, and returns a model select with ID `model`. Available choices depend on that environment/session; an advertised choice does not guarantee a successful billed turn.
- Reasoning uses option ID `effort`, category `thought_level`. The option exists only when the current model reports supported effort levels. For OpenAg's current empty client capabilities, a `default` entry can leave concrete effort to the CLI. Do not display that as a known numeric or named level. Do not opt into extra AIR features just to manufacture a concrete report.
- `setSessionConfigOption` validates against session choices and calls the SDK's `query.setModel` for model changes. The adapter rebuilds effort/capability options afterward. Apply model first, then validate/select effort against the returned choices; a previous model's effort may be invalid.
- The picker may return aliases such as `default`; model labels/descriptions can identify the SDK-resolved model, but a picker ID alone is not an actual served-model ID. Keep the selectable ID separate from display/resolved evidence.
- The adapter records actual assistant `message.model` and emits it as `usage_update._meta["_claude/model"]`. This is stronger per-turn identity evidence than a saved setting. It is an adapter-specific extension, so absence must be handled. Its existence in source is not proof that every turn emits it (failed, synthetic or output-free turns may not).
- Model initialization also considers inherited `ANTHROPIC_MODEL`. OpenAg clears Claude settings sources, but does not strip this variable. Planning must account for administrator environment and session-reported effective configuration, without reading or exposing credentials.

Version-pinned upstream: [model discovery/config builder](https://github.com/agentclientprotocol/claude-agent-acp/blob/v0.97.0/src/session-model.ts), [effort capabilities](https://github.com/agentclientprotocol/claude-agent-acp/blob/v0.97.0/src/session-effort.ts), [adapter implementation](https://github.com/agentclientprotocol/claude-agent-acp/blob/v0.97.0/src/acp-agent.ts). ### Codex adapter 2.3.0

- Model discovery calls the underlying App Server's paginated `model/list`. Session config uses option `model` plus `reasoning_effort`; supported efforts and defaults come from each model record. The adapter updates the effort list after a model change.
- Current model/effort on thread creation/resume comes from the App Server response. Model selection validates against the advertised list. The next prompt passes `model` and `effort` to `turn/start`. An acknowledgement changes adapter session state; it does not run inference.
- Important evidence limit: `buildQuotaMeta` labels `quota.model_usage` using `sessionState.currentModelId`. That label is derived from session configuration, not an independently observed provider response. It must not be presented as proof of the backend that served a turn. The inspected v1 adapter path does not establish an independent served-model report; label it session-reported/acknowledged and retain Not reported for stronger evidence that is absent.
- Do not split model IDs or guess reasoning from names: the adapter already separates model and effort in config options. A legacy unstable set-model method exists, but stable config options suffice.
- Environment can influence the underlying runtime: `CODEX_CONFIG`, `MODEL_PROVIDER`, `CODEX_PATH`, and the local Codex configuration. These remain administrator-managed. No environment/config values or live login state were read in this research.

### Questions the plan must resolve

1. **Discovery before a first turn:** ACP choices require initialization/session setup. Decide the explicit user-triggered setup path, bounded lifetime and disposal behavior. It must not generate a turn, silently launch on unrelated settings reads, or borrow an active session unsafely.
2. **Defaults versus room state:** distinguish a bot's persisted next-session configuration from each existing session's report. The ticket's idle change requires invalidating old bot sessions; future displays must not carry their reports forward as current.
3. **Evidence labels:** use requested configuration, environment override, session acknowledgement and actual response identity as separate evidence. Supported reasoning configuration is often observable when an independently returned effort is not. Do not equate reasoning tokens/thinking text with effort.
4. **Catalogue and availability:** upstream/installed capabilities can validate syntax/features; they do not prove account entitlement, credit, regional access or successful inference. Real-runtime acceptance remains separately authorized and required.
5. **Atomicity and failure:** configuration storage, process teardown and remote/session acknowledgements are not one DB transaction. Define the recoverable state and readback after failure or uncertainty; never show a successful effective switch merely because persistence succeeded.

## Composer model controls (OA-404)

Full access devices can change the addressed agent's model and enumerated effort/thinking settings in the chat composer. Opening a control loads choices; a selection saves the agent's configuration through the same revision/snapshot checks as Settings. This applies across that agent's chats, not just the next message. It requests a configuration; reports remain separate evidence of what a provider/session returned. Chat follows the official shadcn model-selector composition: DropdownMenu radio groups, provider headings/separators, checked items and InputGroupButton triggers. Chat uses CPU/brain icon-only triggers with current selections in accessible names and tooltips; Settings retains text selectors. Agent settings, creation and room routing use the same grouped DropdownMenu selection; model menus have no search field. Numeric budgets remain in Settings.

A direct chat addresses its agent. A single explicit member mention selects that agent; otherwise an unrouted room addresses its lead. Everyone, multiple mentioned agents and dynamically routed messages show no single-agent model control. Limited devices retain chat but cannot edit model configuration. Environment overrides and active/unresolved-work locks remain authoritative.

The message and attachments stay mounted during configuration. Send and message editing are held while a model operation or unsaved configuration draft is pending. A refused/uncertain save preserves the configuration draft and offers explicit readback/reload; no automatic write retry occurs. A confirmed save refreshes the option snapshot for the next change. Chat adds no success message or toast. The model icon shows loading and a screen-reader-only status announces the pending operation without adding a visible row. Passive peer changes update a clean composer. Settings keeps its explicit Save action and any existing local draft.

Composer and Settings serialize configuration requests for the same agent. A mounted clean editor follows confirmed configuration updates; a genuinely edited draft remains staged. Effort choices stay disabled until their snapshot is ready. Mention insertion cannot bypass a pending configuration. Keyboard focus returns to the message after a confirmed change when no other control has taken focus; unresolved drafts keep explicit recovery available.

### Cancelled historical tools

Inactive cancelled Work with a missing tool result is recoverable through Needs you → Recovery → Mark as reviewed. A matching acknowledgement releases that Work item's historical pending-tool model lock while retaining its interrupted state and missing result. The shared Recovery issue key includes the cancellation timestamp and latest call event; new evidence requires a new review. This does not release active-work, admission, approval, question or receipt guards, inspect a receipt, or authorize a retry. See [Needs you](attention/README.md).
