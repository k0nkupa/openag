# MCP client (OA-114)

Verified against `@modelcontextprotocol/sdk@1.32.2` type definitions in `apps/daemon/node_modules` (not from memory).

## SDK surface used

| Need | Import (daemon, ESM) | Verified signature / note |

## Client methods

- `listTools(params?, options?)` -> `{ tools: { name, description?, inputSchema, annotations?, ... }[], nextCursor? }`. Paginate with `nextCursor`.
- `callTool(params: { name, arguments? }, resultSchema?, options?: { timeout?: number })`. Pass `undefined` for `resultSchema`. `timeout` in ms; on expiry the SDK rejects with `McpError` (`RequestTimeout`).
- Result: `{ content: Array<{ type: "text", text } | { type: "image" | "audio" | "resource" | ..., ... }>, isError?: boolean, structuredContent?, _meta? }`. Tool-level failures arrive as a normal result with `isError: true`, not as a thrown error. Protocol failures throw.
- Tool annotations (`readOnlyHint`, etc.) are server-provided and are IGNORED for classification by this daemon.

## Dependencies

- SDK peer/deps: `zod: ^3.25 || ^4.0` (daemon uses zod 4.6.7, compatible).

## Operational rules implemented

- Config file: `$OPENAG_DATA/mcp.json` only. The owner (and a Full device) can add, edit, switch and remove CUSTOM servers through the management routes below (ADR 0003); built-in and managed connections cannot be written that way, and no other caller can write the file.
- Permissions: the file must be owned by the daemon user and not group- or world-writable. Otherwise nothing loads and status reports `refused`.
  Operator should run `chmod 600 $OPENAG_DATA/mcp.json`.
- stdio child env: ONLY `PATH`, `HOME`, `LANG`, `TMPDIR` from the daemon, plus the server's resolved `env`. The daemon's full environment is never passed (it holds `OPENAG_TOKEN` and API keys).
  The SDK's `StdioClientTransport` cannot do this: it always merges its own sudo-style set (`LOGNAME`, `SHELL`, `USER`, `TERM`, ...) into the child. So `src/mcp/exact-env-stdio.ts` spawns the child itself with the SDK's `ReadBuffer`/`serializeMessage` framing.
  On macOS the child may also show `__CF_USER_TEXT_ENCODING`; CoreFoundation adds it to every process, it is not inherited.
- Child stderr is discarded (`stderr: "ignore"`) so server output never reaches daemon logs.
- `${NAME}` references resolve from the daemon environment at connect time. A missing or empty variable skips the server (`skipped: missing env NAME`) without calling the connector.
- Connect has a 15 s limit. Each tool call has an active execution budget of `timeoutMs` (default 30 s). Supported server input pauses that budget within a shared two-minute human-wait allowance and an absolute invocation deadline. SDK cancellation and deadlines bound the full call.
- A server that closes or exits is marked `down` and its tools fail with `tool <name> is not enabled`. The manager does not auto-restart; `POST /mcp/reload` retries.
- Tool output is wrapped as untrusted data (`untrusted: true`, `source: "mcp:<id>"`), preserves text, structured data and the error flag, and is passed through the redactor. The envelope is valid JSON capped at 20 000 characters, with explicit omission/truncation metadata for unsupported or large content.

### Owner management routes (OA-454)

`POST /mcp/servers`, `PATCH /mcp/servers/:id` and `DELETE /mcp/servers/:id?digest=` (owner only, `src/mcp-servers.ts`) add, edit, switch and remove custom servers; `GET /mcp/servers` adds an editable view (`entries`: URL, header NAMES with their `${NAME}` templates, flags, and the file `digest`) for the owner only.

- Remote http servers only. A custom stdio server is read-only from the desk (no edit, switch, agent switch or removal; enabling one would run a command from an HTTP request) until OA-456's command review exists; it stays managed in `mcp.json`.
- Built-in (`openagPackage`) entries and the Composio connection answer 409 (managed elsewhere); unknown ids 404; reserved ids (`openag`, `composio-connect` and the built-in connector ids `local-reference`, `apple-apps`), unknown body keys, plain http without `allowPrivateNetwork`, credentials or references in the URL, a value that contains a redaction marker (the owner's editable view is redacted, so sending it back unchanged would otherwise save the marker), a credential-looking URL query parameter (`token`, `secret`, `key`, `passw`, `auth`, `sig` with a value; the redactor ignores URL-shaped values, so this is checked by name) and daemon-secret header references 400.
- A reference that is NEW in a header must be `OPENAG_MCP_<NAME>`; a reference already in the entry may stay, unless the edit moves the server to a different origin, in which case every reference is new (an old `${GITHUB_TOKEN}` cannot be repointed at another host). `OPENAG_MCP_*` variables are stripped from bot processes.
- Writes go through `src/mcp-config-write.ts`, shared with the local setup command: the `.integration-setup.lock` directory (a busy or stale lock answers 409 and is never removed), a digest compare-and-swap (`digest` in the body or query; a stale one answers 409 "review again"), a backup in `setup-backups/`, an atomic rename, and entries in `setup-audit.jsonl`. The audit `started` line is written BEFORE the file is replaced (an unsafe or full audit file refuses the change with nothing modified, 409); after the rename nothing can throw, so the running server, approval expiry and the ledger event always follow a changed file. Entries are changed as raw JSON items: other entries, unknown fields, values and key order are preserved, but the file is re-written as pretty-printed JSON, so hand formatting is not.
- At most 50 servers. Adding an id that already has top-level `toolClasses` overrides is refused, and removing a server drops its overrides, so a reused id never inherits classifications.
- After a write only that server is reconnected (`applyServer`); other servers stay live and their classification overrides are not re-read until a reload. An unreadable file leaves every live server as it is. Pending approvals for `mcp.<id>.*` are expired. ACP sessions are invalidated only when the set of tools offered to bots changed (the server was or is ready with `offerToAgents`).
- `offerToAgents` defaults to true for every entry; forwarding to ACP bots is wired in a later slice.
- Audit events (`_system`, `mcp_server_added|updated|removed`) carry the id and header NAMES, never values.

### Server check (OA-454)

A server check is a tool action (`src/mcp-check.ts`, `src/mcp.ts` `checkServer`). `POST /mcp/servers/check` (owner only; body: `url`, optional `headers`, `allowPrivateNetwork`, `timeoutMs`, and an optional `id` naming the server being edited) validates the candidate like a write (remote http only; a command server cannot be proposed and `checkServer` refuses one itself) and returns 202 with an `approvalId`. Nothing is contacted yet.

- The candidate follows the write rules, including the reference rule: references already on the server being edited stay only while the URL keeps its origin; pointing the check at a new origin makes every reference new, so an existing variable (for example `${GITHUB_TOKEN}`) can never be sent to a different host. A proposal the redactor would rewrite (for example `session_token=${OPENAG_MCP_X}`) is refused, because the approval stores a redacted copy and what ran would differ from what was approved; a stored payload that contains a redaction marker is also refused at run time.
- The approval is `mcp_server_check`, class `act-external` (never auto), `source` `mcp-server-check`, no turn. Only approvals with that marker are ever run or shown as "you asked"; a lookalike tool name from elsewhere is not. It sits in the delivery room (the hidden `_system` room when there is none, which is not a visible conversation; its initiating settings dialog still owns the check) with the URL, header NAMES and their `${NAME}` templates (stored as name/template pairs because the redactor masks Authorization-style keys). It uses the default bot's id, so a pending check stops model changes for that bot until it is decided or expires. At most 5 wait at once; an unanswered one expires after 5 minutes, and a restart re-arms or expires pending ones.
- Only accepting it runs the check, once, from the STORED payload. Ignore, respond and expiry never contact the endpoint. The daemon connects through the same guarded connector, lists the tools and closes; it registers no server, offers no tool, and writes nothing to `mcp.json`. Approving a check does not approve any tool action the server offers.
- The action receipt is never started, only finished (`completed`, `failed`, or `not-run` for a refused row): starting it would mark an external action as running and block every other external action, and a restart mid-check would leave an `unknown` receipt that blocks them until inspected. Startup recovery closes an unfinished check receipt as `not-run`.
- `GET /mcp/servers/check/:approvalId` (owner only, no-store) returns `pending | running | declined | expired | done` with, when done, `ok` and either up to 50 tool names with 200-character descriptions (untrusted text: render as plain text) or a fixed reason (`connect failed`, `connect timed out`, `list timed out`, `missing env NAME`, a guard reason). Declined, expired and finished results stay readable for 15 minutes, in a map of at most 20 entries that never evicts a pending or running check.
- A failed or refused check is a redacted `_system` `config` event (`mcp_server_check_failed`, id and reason only), not a separate queue item; a completed one records `mcp_server_checked` with the tool count.
- Only the owner or a Full device can decide a server-check or command-review approval. Limited devices cannot initiate the proposed network check; results remain owner/Full-only.

Check: `node scripts/verify-mcp-management.mjs`.

### Offering servers to agents (OA-454)

Each server has an `offerToAgents` switch, default true for every entry (`mcp.json`, shown in the owner's editable view). It means one thing everywhere: with it off, the server's tools are absent from every runtime's offered list (API, Ollama and ACP) and its executor refuses with "not enabled"; the server itself stays connected and visible in status.

Claude and Codex (ACP) bots receive MCP-client tools through the daemon's own `/mcp` server (`src/mcp-forwarding.ts`) only for servers that are connected, have the switch on, and are a custom server, the Apple package or the Composio connection. The built-in `local-reference` example is never forwarded. A name that belongs to a first-party or App tool is dropped, a duplicate is offered once, and a custom server's description is collapsed to one line (the manager already prefixes it with `[MCP <id>; class ...]` and caps it at 300 characters). Forwarding offers a tool; every call still goes through the daemon's gate, and since the session permission modes an MCP operation (which cannot enforce a filesystem boundary) is refused in the confined modes and runs without a human approval in Full access. A custom tool defaults to `act-external` and the owner can declare it `read` or `search` in `toolClasses` (this decides how an unconfirmed result is reported and whether it is fenced after an unknown receipt), and Composio's reviewed discovery tools are read-class; `verify-acp-tool-identity` exercises the gate for `mcp.<server>.<tool>` names with synthetic definitions. The Apple health check the owner runs from the desk uses `ownerToolDefs()`/`ownerExecutors()`, which ignore the switch: it is an owner action, never an offer.

A change to what is offered reaches a running bot because `/mcp` rebuilds its list on every request, and the adapter's cached list is reset when `onChange({ offeredChanged })` fires (a server that was or is ready with the switch on). Check: `node scripts/verify-mcp-forwarding.mjs`.

### Remote server address guard (OA-454)

Every http server (the `mcp.ts` default connector) reaches the network only through `src/mcp/ssrf-fetch.ts`:

- `https` is required. Plain `http`, loopback (`127/8`, `::1`), LAN (`10/8`, `172.16/12`, `192.168/16`, ULA `fc00::/7`, deprecated site-local `fec0::/10`) and CGNAT/Tailscale (`100.64/10`) need the owner's per-entry `"allowPrivateNetwork": true` (it also permits plain `http` to any host the guard otherwise allows); without it `http:` is invalid (`http requires allowPrivateNetwork`) and a private target is `down` with the fixed reason `blocked private address`. These are refused even with the flag, as are credentials in the URL: link-local and cloud-metadata hosts (`169.254/16`, `fe80::/10`, `fd00:ec2::254`, `100.100.100.200`, `192.0.0.0/24` incl. `192.0.0.192`), unspecified and multicast space, and documentation or reserved ranges (`192.0.2/24`, `198.51.100/24`, `203.0.113/24`, `192.88.99/24`, `198.18/15`, `240/4`, `100::/64`, `2001:db8::/32`, Teredo `2001::/32`, local-use NAT64 `64:ff9b:1::/48`). Other cloud-metadata hosts a provider might add later are not enumerated; an owner who enables the flag on a cloud host should also rely on that provider's own metadata protections.
- The check judges the parsed hostname, so hex, octal and integer IPv4 forms, IPv4-mapped, compatible and SIIT-translated IPv6, NAT64 (`64:ff9b::/96`), 6to4 and Teredo are all unwrapped or refused. An unparseable address fails closed.
- Hostnames are resolved at connect time by a pinned `lookup`: every answer must pass, and only the checked addresses reach the socket, so a name that later resolves private (DNS rebinding) is refused.
- Redirects are never followed by the guard (`redirect: "manual"`); the SDK's same-origin policy re-enters the guard for each hop. Never configure `follow`.
- Status text shows only a fixed reason, never the URL, host or address.
- The Composio connection is unchanged: it uses its own fixed hosts and `redirect: "error"`. Stdio servers have no network surface here.
- Existing hand-written http entries that point at a private address stop connecting until the owner adds `allowPrivateNetwork: true`.

### Environment references in http headers (OA-454)

`${NAME}` in an http server's `headers` may not name a daemon secret: the entry is `invalid` with `header references a daemon secret (NAME)` (the name, never a value). Refused names are `isForbiddenHeaderEnvName` (`src/secret-env.ts`): every `OPENAG_*` variable plus `isDaemonSecretEnvName`, i.e. the owner token, connector key, model-provider variables, every `*_API_KEY`, and the sign-in, Google, Composio, SSH, RTC, Browserbase and Slack families. `isDaemonSecretEnvName` also backs `withoutOwnerSecrets` and `claudeEnv`, so the bot environment and the daemon-secret part of the header rule cannot drift (the header rule adds the wider `OPENAG_*` prefix; bots keep non-secret `OPENAG_` settings such as `OPENAG_PORT`). Known limit: this is a denylist, so other daemon variables with no daemon-secret name (for example `GITHUB_TOKEN` or `AWS_SECRET_ACCESS_KEY`) can still be referenced from a header by an operator; a per-server allowlist for the desk write API is an open decision. A remote server's key therefore needs its own variable name (for example `MCP_LINEAR_TOKEN`), not `LINEAR_API_KEY`. Stdio entries are unchanged: their `env` may still reference an API key (the shipped Brave example does) because a stdio child is a reviewed command, and url references stay refused. Direct secrets (OA-455) will replace env references for desk-added servers.

Check: `node scripts/verify-mcp-env-refs.mjs` (standalone; fails when the denylist or the shared predicate is broken).

Check: `node scripts/verify-ssrf-guard.mjs` (standalone, no external network; it fails when the guard is deliberately broken). It also pins the SDK behaviour the guard relies on: same-origin redirect hops re-enter the guard, cross-origin redirects are never followed, and no code configures `follow`.

### Direct secrets (OA-455)

`${secret:NAME}` (`^[A-Z][A-Z0-9_]{0,63}$`) in an http header value refers to a secret stored in `connector-mcp.enc` (`src/mcp-secrets.ts`): the connector credential store, AES-256-GCM with its own AAD, encrypted with the existing `.connectors/key` (no second key; `resolveConnectorKey` knows the `mcp` store, so a missing key with an existing store is a recovery error, never a silent new key). The record is `{version, servers: {<id>: {<NAME>: {value, origin}}}}`; at most 40 secrets, values 12 to 1024 characters with no spaces or control characters (a value the redactor cannot match, such as a short, spaced or path-like one, is refused so a server cannot echo it back unmasked). `PUT` may carry the `origin` the owner was looking at; a different current origin is a 409 instead of a bind (the desk always sends it).
- Routes (owner/Full only, `no-store`): `GET /mcp/secrets` (server id, name, origin, last four when the value has 12+ characters, else null), `PUT /mcp/secrets/:serverId/:name` `{value}`, `DELETE /mcp/secrets/:serverId/:name`. A value never appears in any response, ledger event (`mcp_secret_set|removed`: id and name), audit line or approval payload. The secret is registered with the redactor before it is saved and again at startup.
- Binding: a secret is bound to the ORIGIN the server had when it was stored and resolves only for that server id AND origin (`get(id, name, origin)`), so repointing the entry by hand cannot send it elsewhere. A desk edit that changes the origin, and removing the server, delete its secrets inside the config write (same `.integration-setup.lock`), so an id reused later inherits nothing.
- Fail closed: an unset, deleted, wrongly bound or unreadable secret skips the server (`missing secret NAME`) without any connection. Env references (`${NAME}`) keep their own rules; both kinds resolve in ONE pass, so a value that itself contains `${...}` is never expanded again.
- `checkLiteral` still rejects plaintext that looks like a secret; `${secret:NAME}` is accepted only in http headers (not URLs, and not stdio fields until OA-456). The server check carries the template only; it resolves stored secrets for the saved server and its current origin.
- Credential cleanup participates in the synchronous config transaction. A refused audit or failed config replacement restores the previous credential records before releasing the writer lock. While the store is unreadable (key needs recovery), a desk repoint or removal returns 503.
- Backups: the file lives outside SQLite and its backups, like the other connector stores; the key stays on the host.

Check: `node scripts/verify-mcp-secrets.mjs` (11 groups, standalone) and the secret group of `node scripts/verify-mcp-desk.mjs`; mutations of the binding, the drop-on-move and the redactor registration make them fail.

### Local commands from the desk (OA-456)

`POST /mcp/servers/command-review` (owner/Full only, `src/mcp-command-review.ts`, `src/mcp-command-review-core.ts`) proposes; `GET /mcp/servers/command-review/:approvalId` returns `pending|running|declined|expired|done`. Body: `{id, command, args, env, timeoutMs?, offerToAgents?, enabled?}`.
- Proposal rules: `command` is a PATH name (looked up in the daemon's PATH) or an absolute path, resolved to a realpath that must be an executable file; shells (`sh`, `bash`, `zsh`...) are refused, wrappers (`env`, `nohup`, `sudo`, `xargs`...) are refused; an interpreter (`node`, `python3.x`, `perl`...) needs an EXISTING script given by its absolute path as its FIRST argument (no leading flag, so no `-e`/`-c`, and nothing that does not exist yet); a program that is itself a script (`#!`) has its own content hashed; env names that load code or change startup (`PATH`, `HOME`, `NODE_*`, `PYTHON*`, `LD_*`, `DYLD_*`, `PERL*`, `RUBY*`, `BASH_ENV`...) are refused; no `${...}` in the program or arguments; env values may reference only `OPENAG_MCP_*` or `${secret:NAME}`; at most 3 existing absolute-path arguments are hashed by content (each at most 1 MiB).
- The review (`review` in the entry, `ReviewRecord`): `hash` = sha256 of `{command, executable, args, sorted env templates, cwd "mcp-work/<id>", files}`, `executable` (realpath), `binding` (sha256 of command, executable, args, files: what stored secrets are bound to), `files` (each `{arg, path, sha256}`; the loader re-resolves `arg`, so a symlink repointed at other code is a change). It is shown in the approval (`mcp_command_review`, `act-external`, source `mcp-command-review`, no turn, 5 min, max 5 pending) as argv, env names with templates, `$OPENAG_DATA/mcp-work/<id>`, the hash and the warning that it runs on the daemon host with the owner's permissions and is not sandboxed.
- Apply: only an accepted approval from this module writes, and it writes the STORED payload through `updateMcpConfig` (lock, digest, backup, audit `desk-command-approved`): the review is rebuilt and must hash the same, a replaced entry must still be the desk command it was proposed against (`replacesHash`), an id held by an operator entry or a remote server is refused, and a program/argument change drops the server's secrets. The working directory `mcp-work/<id>` is created mode 700 through `managedPath`.
- Run: an entry with `managedBy: "desk"` is `invalid` (`command not reviewed`, `command changed since it was reviewed`, `a reviewed file changed since it was reviewed`, `the reviewed program is no longer available`) unless `reviewProblem` passes, at load and in `connectRecord` before each spawn. It spawns the reviewed realpath with `cwd = $OPENAG_DATA/mcp-work/<id>` through `ExactEnvStdioTransport`: environment is PATH/HOME/LANG/TMPDIR plus the declared names only (macOS itself adds `__CF_USER_TEXT_ENCODING`).
- Deciding: only the owner (a Full device counts) may accept, ignore or respond to a `mcp_command_review` approval (`POST /approvals/:id` returns 403 otherwise); there is no edit validator, so an edit decision cannot change what is written. The desk withdraws a proposal that is no longer on screen. An edit keeps a switched-off server off, does not inherit the old `timeoutMs`, and drops `toolClasses[id]` when the program or arguments change.
- Edit and removal: command, arguments and environment change only through a new review (PATCH refuses them; also `url`, `headers`, `allowPrivateNetwork` on a command). Enable/disable, `offerToAgents`, `timeoutMs` and removal are direct. Operator-written commands (no marker) are never editable, replaceable or removable from the desk.
- Limits: files a script imports, and what `npx`/package managers download, are outside the hash; a PATH change re-resolves only at a new review (the reviewed realpath is what runs); the child is not sandboxed; removing a command leaves its working directory.

Check: `node scripts/verify-mcp-stdio.mjs` (8 groups, real stdio child), the local-command group of `node scripts/verify-mcp-desk.mjs`, and `node scripts/verify-mcp-custom-real.mjs --stdio [--real]`; mutations of the loader gate, the hash recheck at write, secret drop, shell refusal, the approval source and the file-content check each fail them.

### OAuth sign-in for custom remote servers (OA-457)

An http entry may carry `oauth: {scope?, clientMetadataUrl?}` (`src/mcp-oauth.ts`; no secret in `mcp.json`). Routes (owner/Full only, `no-store`, none returns a token or code): `GET /mcp/servers/:id/oauth` (state, issuer, registration kind, whether an owner client exists), `POST /mcp/servers/:id/oauth/start|status|cancel|disconnect`, `PUT|DELETE /mcp/servers/:id/oauth/client` (owner-entered client; the secret is write-only). The callback is the shared `/composio-connect` path (hosted relay and Tailscale handler unchanged); the daemon dispatches by exact state, so an unknown state costs nothing and a Composio attempt is unaffected.
- Discovery (`discoverOAuthServerInfo` through the guarded fetch with `allowPrivateNetwork` of the entry, 15 s and 64 KB per response): refused unless every endpoint passes `checkUrl` (https, or plain http only with the owner's private-network opt-in, no credentials or fragments), `metadata.issuer` equals where it was discovered, `code_challenge_methods_supported` includes S256 (absent is refused), the authorization-code flow is supported, and the protected resource is on the server's own origin. An entry that has not opted into private addresses cannot sign in to a loopback server.
- Registration: an owner-entered client first (bound to the server's origin), then a client metadata document (only when `oauth.clientMetadataUrl` is an https URL AND the server advertises `client_id_metadata_document_supported`), then dynamic registration with `application_type: "web"`, `token_endpoint_auth_method: "none"` and the managed callback as the only redirect URI. Operators: a metadata document is the owner's to host at a public https address; OpenAg does not host one.
- Attempt: in memory (a restart means signing in again), 5 minutes, single use, bound to the starting device, at most 5 open; the browser is sent only to an address discovery validated. `state` and RFC 9207 `iss` are checked before the code is exchanged: a present `iss` must equal the issuer, and a missing one is refused when `authorization_response_iss_parameter_supported` is true. A hosted route is read by polling the mailbox with the same checks.
- Tokens: `connector-mcp-oauth.enc` (`mcp-oauth` store, AAD `OpenAg MCP OAuth v1`, the existing connector key; a missing key with an existing store is a recovery error). Record per server: origin, issuer, resource, redirect URI, registration kind, client, tokens, expiry, `needsSignIn`. Every token, code, state, verifier and client secret is registered with the redactor.
- Use: the manager connects an OAuth entry through `oauth.connect`, which injects `Authorization: Bearer` per request. Refresh is single-flight per server and re-validates discovery; only the record it started from may be replaced. A 401, a 403 `insufficient_scope` (the scope is kept as a hint) or a rejected refresh (`invalid_grant`, `invalid_client` and similar) sets `needsSignIn`; a network failure or `server_error` leaves the grant alone. The request that found out is not retried, so nothing is replayed. A desk server shows `skipped` with `needs sign-in`.
- Cleanup: removing the server, moving it to another origin, turning OAuth off or saving an owner client for it deletes its grant; an id reused later inherits nothing. Disconnect clears local tokens and client info only; the provider is not asked to revoke (unconfirmed).
- Details: only a resource the server advertises is sent as the resource indicator. A grant with no `expires_in` and no refresh token is treated as non-expiring; one with a refresh token but no `expires_in` is refreshed after about an hour. A failure only marks a server `needs sign-in` if the credential that failed is still the stored one, so a late 401 for an older token never wipes a newer sign-in. MCP traffic uses the plain guarded fetch (large tool lists, long calls); the 15 s and 64 KB limits apply to the OAuth calls only. Removing the owner-entered client also removes a grant that used it.
- Limits: real provider consent and the hosted relay are unverified; every server (and Composio) shares one redirect URI, so protection against a provider mix-up rests on the provider sending `iss` (checked whenever it is advertised or present); a stolen Full device can sign in; scope changes on an existing entry apply at the next sign-in; a sign-in start aborted while it runs can hold one of the 5 open slots until it expires.

Check: `node scripts/verify-mcp-oauth.mjs` (11 groups against `scripts/mcp-oauth-fixture.mjs`, a controlled fake authorization server), the OAuth group of `node scripts/verify-mcp-desk.mjs`, and `node scripts/verify-mcp-custom-real.mjs --oauth [--real]`.

## Trusted classification and completion (OA-379)

Classification controls permission, independently of invocation completion and confirmation of an external effect. Defaults remain Auto for trusted read/search/browse, Ask for external actions and unknown tools, and Deny for secrets; stricter bot modes still apply. Remote hints, descriptions and response fields never change a class. A query response does not prove permission for another operation or authorize a write.

The existing owner-controlled `mcp.json` supports both per-entry `toolClasses` and an optional top-level map keyed by server id and **original remote tool name**:

```json
{
  "servers": [],
  "toolClasses": {
    "example": { "FIND_ITEMS": "search", "SEND_ITEM": "act-external" }
  }
}
```

The top-level map applies to configured and daemon-managed connections and overrides their per-entry declarations. It cannot configure transport, replace reserved endpoints, install a connection or grant ownership. Existing entries without the map remain compatible. The same ownership/permission checks protect the whole file; there is no HTTP setter. Only an administrator who has reviewed the operation's contract should declare it read/search/browse. The managed Composio connection has a reviewed declaration covering its twelve known shared tools. `COMPOSIO_SEARCH_TOOLS` and `COMPOSIO_SEARCH_SKILLS` are Search; `COMPOSIO_GET_TOOL_SCHEMAS` and `COMPOSIO_USE_SKILL` are Read. Execution, connection/wait, proxy, shell/workbench, skill-change and feedback tools are declared external actions and remain approval-gated. It is contract data for the shared policy path, not a separate permission engine. A reported active provider connection does not establish mailbox scopes or prove a mailbox read.

A non-error MCP reply completes its invocation regardless of the tool's permission classification or name. `isError` fails the invocation. Returned evidence stays redacted, capped and untrusted, with daemon-owned `effectVerification: not-checked` in the result, receipt evidence and ledger/runner outcome. This field is retained through scoped ACP MCP, API and Ollama delivery, including bounded results. External effects have not been independently verified; successful invocation neither grants action authority nor authorizes a retry. A transport timeout/disconnect without a returned result can still be Unknown and never claims `invocationOutcome: returned`. Historical Unknown receipts stay unchanged. No path automatically retries a call.
